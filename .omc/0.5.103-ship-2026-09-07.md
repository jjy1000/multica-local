# 0.5.103 — board count/body parity + Pythia engine auto-start (2026-09-07)

Two user-reported symptoms from the 2026-09-07 15:11/15:12 screenshots,
both root-caused on the live 0.5.102 install before any code change.

## Symptom 1 — board badge counts over empty columns

My-Issues board: all four columns (待规划/待办/进行中/审核中) badged "92"
with "无 issue" bodies; workspace board badged the workspace total in
every column. Verified live against the running 0.5.102 backend:

- `GET /api/issues?status_category=todo` → `total=425` (param ignored)
- `GET /api/issues?status=todo` → `total=2` (singular form worked)
- `project_ids=<uuid>` → `total=425` (ignored)

### Root causes

1. **status_category never reached the server.** `fetchFirstPages` fans
   out one `GET /api/issues?status_category=<cat>` per category, but
   `api.listIssues` never serialized the param AND the server's
   `ListIssues` only parsed singular `status` (`statuses`/`status_category`
   /multi-value filters lived exclusively in `ListGroupedIssues`). All 7
   buckets received the same global first page + workspace-wide total.
   **This is the true source of the 0.5.102 "create one issue → N
   duplicate cards" incident** — `d6f918c6c`'s 3-layer dedupe treated the
   symptom while every bucket still held the same global list.
2. **Count ≠ body under filters.** The badge reads `bucket.total`
   (unfiltered) while cards pass client-side `filterIssues`; the user's
   persisted "1 个筛选" stripped every loaded card.
3. The uncommitted MUL-6409 WIP in the working tree pushed the board
   filter down to `listIssues`, but (a) the server endpoint ignored those
   params and (b) `PaginatedBoardColumn`'s `useLoadMoreByStatus` still
   read the `{}` cache key while `IssuesPage` wrote the filter-scoped key
   — internally inconsistent.

### Fix (commit `0b29633ec`)

- Server `ListIssues`: parses `status_category`/`status_categories`
  (via `issuestatus.ExpandCategories`), `statuses`, `assignee_filters`,
  `include_no_assignee`, `creator_filters`, `project_ids`,
  `include_no_project`, `label_ids` — WHERE fragments copy-for-copy from
  `ListGroupedIssues`, count query shares the same WHERE. Regression:
  `TestListIssuesStatusCategoryAndActorFilters` (actor-scoped totals so
  the shared test workspace can't leak into assertions; `in_review` is
  the category key — `review` is not).
- Client `listIssues` serializes `status_category`/`status_categories`.
- `useLoadMoreByStatus` gains `workspaceFilter`: badge read, load-more
  cache key, and load-more request all resolve to the same filter-scoped
  row the page queried; load-more narrows by `status_category` (not
  literal `status`) to match the first-page fan-out. Board/list/swimlane
  thread `statusColumnFilter` from `IssuesPage.boardFilter`.

## Symptom 2 — Pythia 预演 "引擎不可用，结果为本地回退数据"

JYF-452 dispatch to `pythia_runtime` completed (comment posted, R1–R10
progress bars) with `server.log`:
`pythia forecast: persist run OK ... rounds=10 source=synthetic`. The
report's 概率 98%/105%/112% = `0.42 + round*0.07` exactly (confidence
hardcoded 0.55) — the entire run was the server's synthetic fallback.

### Root causes

1. The engine subprocess's only bring-up path was opening the Pythia lab
   panel (`pythia-view.tsx` → `pythia:ensure-up` IPC). The
   issue-dispatch path (daemon → `pythia_runtime` → server forecast
   endpoint) never mounts a panel; `renderer.log` had 0 `ensure-up`
   calls this session. `sourceForForecast` found no loopback URL →
   silent synthetic.
2. The synthetic probability formula crosses 1.0 at round ≥ 9 and the
   issue report rendered impossible "105%"/"112%".
3. The issue right rail showed "实验室未启用" for a flag that WAS on —
   the open-panel link was gated on `hides_deliverable_in_issue_timeline`
   (false for pythia BY DESIGN), so pythia-bound issues fell into the
   disabled fallback copy.
4. No visible way to stop a run (the only terminate affordance lives in
   the execution log).

### Fix (commit `d5a90373e`)

- `PythiaEngineAutoStart` (desktop App root): `ensureUp` once when
  `pythia_oracle` resolves enabled, plus listener for the
  `multica:lab-flag-enabled` event the labs settings tab dispatches on
  enable — mid-session toggles no longer wait for relaunch. Boot
  failures stay silent here (lab panel still surfaces them).
- Synthetic probability clamped to `min(0.97, 0.42+0.07r)`.
- `IssueLabsSection` open-panel link gates on `suffix && labEnabled`
  only; the "lab not enabled" box renders only when the flag is really
  off. i18n `lab_section.terminate_running` (en/zh-Hans/ja/ko).
- Section header shows a stop button while a snapshot task is running
  (same `cancelTask` + confirm dialog as the execution log); cancelling
  aborts the agent task whose in-flight forecast request stops the
  server round loop via request context.

## Rider: repocache tests vs global core.hooksPath (commit `03965d94b`)

`TestGatedHookHonorsStateFileAtCommitTime` +
`TestCreateWorktreeInstallsCoAuthoredByHook` failed at clean HEAD —
verified pre-existing via stash. Cause: `~/.gitconfig` now carries a
global `core.hooksPath` → Codex template dir, redirecting hook lookup
for every repo without a local override; the daemon-installed
prepare-commit-msg hook never ran. Tests now pin `core.hooksPath` in
their repos. **Product follow-up (not decided here): should
`CreateWorktree` defend against user-global hooksPath overrides?** On
this machine the daemon's co-author trailer silently does not apply in
agent worktrees.
