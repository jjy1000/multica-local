## 用户报告与诊断过程

**报告**：截图（2026-08-31 09:21）显示收件箱页面的空态详情区上方悬浮着 issue 操作菜单 + 展开的状态子菜单；用户描述"点击后无反应导致卡死"。

**诊断关键链**（每步都有代码/运行时证据）：

1. 截图取证：菜单悬在收件箱**空态**上——fork 的收件箱页面根本没有打开该菜单的入口（收件箱行无右键菜单、空态无菜单），这个菜单只能是**上一个状态残留的孤儿**。
2. 打包 asar 校验：`/Applications/Multica.app` 0.5.90 内的 inbox 组件与仓库一致（无行级菜单）→ 排除"装的应用代码不同"。
3. 运行时排查：:8090 打包服务器毫秒级响应、进程 CPU 0% → 卡的是渲染进程输入层，不是后端。
4. 根因（fork 代码）：`IssueActionsContextMenu` 在 list-row/board-card/gantt-view **每行**挂一个 ContextMenu 根；Base UI `modal` 默认 `true`（MenuStore.js `state.modal ?? true`）= 打开时挂隐形全屏 backdrop + 滚动锁。菜单自己的"状态"操作触发乐观更新 → issue 重新分组 → **锚定行连同步打开中的菜单根一起卸载** → 卸载路径清理不彻底 → 孤儿 backdrop 吞掉全窗口输入。行卸载的触发面很宽：状态分组重排、看板列间移动、状态过滤、折叠分组、路由切换等。
5. 上游对照（fork 与 upstream 无共同祖先，纯人工 cherry-pick）：上游 **已修复同一类问题**——`ba108978a`（2026-07-28）单例 `IssueContextMenuProvider`，注释原话 "A board remount used to create N × (MenuRoot + Trigger) — **the single largest slice of the tab-switch freeze**"；上游 `inbox-context-menu.tsx` 注释点名"每行一个根会在行滚出视口瞬间把打开的菜单一起卸载"。上游另有相关未移植修复：MUL-6749（非 ASCII 自定义状态名派生 key）、MUL-6835（状态/优先级值 i18n）、`109b67790`（状态筛选菜单 GroupLabel 崩溃）。

## 本周期踩坑与教训

1. **"菜单孤儿"读图法**：菜单出现在一个不可能打开它的页面上 = 孤儿 portal。UI 取证（截图局部放大）比代码穷举更快定位"哪个状态残留了"。
2. **fork 与上游无 merge-base**：`git merge-base` 为空意味着一切对比只能按文件路径逐个 diff，`git log HEAD..upstream` 的 717 提交只是"上游在新历史上的量"，与 fork 的落后程度无直接换算。
3. **Base UI modal 默认值在 store 层**：`state.modal ?? true` 藏在 MenuStore 而非 Root 的 props 默认——只看 wrapper 组件会误以为没有 modal 行为。
4. **并发工作区**：本周期进行时工作区有另一会话的实时在途修改（core/issues/mutations.ts、core/realtime/use-realtime-sync.ts、status-picker、app-sidebar、experimental.json、×2 manifest）。提交一律显式路径 stage；打包前以 typecheck+测试重验工作区。教训：多会话共享工作区时，`git status` 是每步操作的前置事实，不是会话开始时的快照。
