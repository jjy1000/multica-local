## 1. 现状盘点（探查结论摘要，设计的事实基础）

### 已经存在、直接复用的
- **委托闭环端到端已通**（0.5.88）：`multica lab delegate --parent --stage`（`cmd/multica/cmd_lab.go`）→ 子 issue 携带 `parent_issue_id + lab_source` → `RecordDelegationEdge` 写 `depends_on` 边（provenance `issue_delegate`，幂等）→ 子终态经 `notifyParentOfChildDone`（`handler/issue_child_done.go`）在父 issue 发 mention 系统评论唤醒父 agent → CLI 轮询终态后回传 `[lab delegate]` 结果评论（2000 rune cap）。
- **"按特点调用"的法律已经成立**：`BuildDelegateBrief`（`service/causal_graph/delegate_brief.go`）只列 assignee 型 + 非 frozen + AutoDispatch≠false + leader 可解析的实验室；CLI 同步 fail-fast。auxiliary 型（causal_graph、llm_wiki_bridge）与 AutoDispatch=false（pythia_oracle、timesfm）天然不可主动委托——正是"因果决策等不属于主动性调用"的机器化表达。
- **隐藏机制完备**：`experimental_resource_visibility` 行 → `filterLabsHiddenByDefault` 列表过滤 + `lab_managed` DTO 打点（Active Contract #4 强制所有 selection surface 过滤）。mythos 5 agent + swarm role agent + causal 三人组 + 用户插件 capabilities 全走这条路。
- **启停**：`PATCH /api/experimental-flags/{key}`（per-user `experimental_pref`），installable lab 同时触发 install/rollback。用户不可删内置 flag（编译期 catalog）。
- **用户插件 CRUD**：`user_plugin` 表（mig 166/168 partial-unique）+ `handler/user_plugins.go` + 表单 UI + `multica-lab-builder` 内置 skill（教 agent 用 curl 打 :8090 完成 CRUD）+ `[实验室创建]` issue 入口。删除=软删+清 visibility+清 pref。
- **报告回写先例**：`handler/lab_report_writeback.go::postLabRunReportComment`（pythia/timesfm，mig 282 `report_comment_id` 幂等）。
- **因果图**：Tier A 零 LLM 钩子（task enqueue/complete 全局写入）+ Tier B semantica 决策镜像 + Tier C pythia + Tier D LLM 建议（一律 suggested、confidence≤0.5、never-nag 探针、reject 墓碑）；claim 时 BFS≤2 注入（0.5.85）；单任务决策视图已存在（`IssueCausalGraphIcon` Popover + `/experimental/causal-graph?issue=` 聚焦模式）。
- **LLM 桥**：`/api/runtime/llm-call`（loopback-only，json_schema 先例在 `claude_lab_llm_forecast.go`）；LLM Wiki 桌面 API client（vector+keyword search）+ vault 直写 writer。
- **事实校准**：`claude_science_lab` 自 0.5.81 起 AutoDispatch 已回默认 true（catalog.go 内注释明确），因此科研实验室**已经**出现在 delegate brief 中、可被任意 agent 委托。根 CLAUDE.md Active Contract #6 的"claude_science_lab 是唯一 opt-out lab"表述已过时，本设计批次内同批更正文档（docs-sync）。

### 缺口（本设计要补的）
1. agent 在 claim 时**不知道**自己可以创建/管理插件（briefing 无此节；lab-builder skill 只有在被注入时才知道）。
2. CLI 只有 `lab delegate`，没有 `create/list/enable/disable/delete`——对话式管理没有安全的动作面（skill 教的 curl 无 fail-fast、无回收语义）。
3. **删除不回收**：agent/squad/autopilot/skill 行成为孤儿；`~/.multica/plugins/<slug>/`（env 数据库+artifacts）残留；无回收计划展示。
4. 资源"代建"无收口：agent 手建资源再装进 manifest，登记靠自觉，回收无从谈起。
5. 委托在父 issue 对话流中**不可见**（`delegated_from_task_id` 与 locale `source_delegation` 均无消费者）；进行中状态只有子 issue 里有；LabProgressCard 对 `user_*` 返回 null。
6. 因果"回忆/回溯"无主动通道（claim 注入是唯一读点；`useCausalGraphPath` 无 UI 消费者）；LLM 实体关系抽取不存在；Wiki 与因果图零联动。
7. 科研实验室 UI 有直聊入口（Chat tab `ExperimentalChatPane`）——违背"不允许直接输入实验内容"；无研究历史档案区；科研 run 无报告评论回写。

## 2. 总体原则（红线，全程遵守）

1. **不建平行通道**：委托=子 issue+lab_source+depends_on 边+child-done 唤醒，一切扩展长在它上面。
2. **briefing/CLI never-disagree 法律扩展为五动词**：delegate/create/list/enable|disable/delete——briefing 提到的每个命令必须真实存在且语义一致，用 contract test 锚定（解析 brief 中 `multica lab <verb>` 与 cobra 注册表 diff）。
3. **trust ladder 不可逾越**：LLM 抽取的实体/关系一律 Tier D suggested（confidence≤0.5、`llm_extract` provenance、FindCausalEdgeBetween any-status 探针、reject 墓碑）。永不新增直产 active 的 Tier D 路径。
4. **migration forward-only、config append-only、`user_` 前缀、用户不可建内置 flag**。
5. **污染隔离沿用既有两件套**（visibility 行 + lab_managed 打点），新增第三件：teardown ledger。
6. 每期验证遵循 0.5.88 协议：`pnpm typecheck` 全turbo + `go test -count=1`（`DATABASE_URL` 导出、验证服务器 :8091 停止）+ live API 全环 + Electron UI audit（Playwright `_electron.launch`）。
7. i18n 4 locale 同 commit；selector 箭头表达式；labs 网络 `api.rawRequest`；新 `/experimental/*` 导航 arm release-suppression token（0.5.80 nav law）。

## WS1 — 对话式创建用户级插件（0.5.89）

### 1.1 CLI 扩展（`server/cmd/multica/cmd_lab.go` 增补）

```
multica lab list [--all]                    # 内置+用户插件：key/状态/interaction model/frozen/leader
multica lab create --slug s --title-zh .. --title-en ..
        [--interaction-model auxiliary|assignee] [--leader <agent-name>]

- **agent 上下文护栏**：`inAgentExecutionContext()` 内 `enable/disable` 对**内置** key 拒绝并提示"内置实验室启停请让用户在 Settings→Labs 操作"（防 agent 误触 install/rollback 重型路径）；user_* 插件不受限。`delete` 永远只接受 user_* slug（服务端本来就没有内置 DELETE，CLI 侧同样 fail-fast）。
- `create` 服务端校验完全复用 `ParseUserPluginContract`（assignee 必有 leader、缺省→auxiliary），leader 不存在时错误信息指引 `multica agent create`（代建隐藏 agent 的路径见 WS2.1）。
- create 成功输出 flag_key + "已注入 briefing 的能力清单将随下次 claim 生效"。

### 1.2 claim briefing 增节（`delegate_brief.go` 同族新文件 `plugin_brief.go`）

在 `## Available Labs (delegation)` 之后追加（≤600 字节、200ms 预算、静默降级，同一注入点 `handler/daemon.go::ClaimTaskByRuntime`）：

```
## Lab Plugin Management

You can create and manage user lab plugins for the user from any conversation:

- Create:  multica lab create --slug <slug> --title-zh "<名>" --title-en "<name>" [--leader <agent>]
- List/inspect: multica lab list | multica lab inspect <key>
- Enable/disable/delete: multica lab enable|disable <key> ; multica lab delete <slug> --dry-run (then --confirm)

Plugin-internal agents/skills/automation are hidden from Multica by default and fully reclaimed on delete. Always post a `[lab plugin]` comment describing what you created.

一致性法律（2 号原则）落地：`cmd_lab_test.go` 新增 contract test——渲染 brief 抽取所有 `multica lab <verb>` 记号，逐一断言在 cobra 命令树中存在且 flag 集合一致。

## WS2 — 插件资源隐藏与删除回收（0.5.89）

### 2.1 资源代建收口（消灭"登记靠自觉"）

create 请求的 `manifest.capabilities.agents[]` 允许**内联定义**（name/instructions/model…），服务端在创建插件事务内：
1. 原子 upsert 这些 agent 行（含 leader 本身——`leader_agent_create` 内联定义同理）；
2. 为每个代建资源种 `experimental_resource_visibility` 行（lab_managed，Active Contract #4 自动生效）；
3. **逐条写 teardown ledger**（见 2.2）。
`multica agent create` 的常规路径保持不变；手建资源装进插件的场景提供补充 CLI `multica lab attach-resource <slug> --type agent|skill|autopilot --id <uuid>`（幂等写 ledger）。

### 2.2 Teardown ledger（mig 284，forward-only 新表）

```sql
CREATE TABLE user_plugin_resource (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id UUID NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    plugin_slug TEXT NOT NULL,             -- 逻辑外键 user_plugin(slug)，软删后仍需可查
    resource_type TEXT NOT NULL CHECK (resource_type IN ('agent','squad','autopilot','skill','env_dir')),
    resource_id UUID,                      -- env_dir 型为 NULL
    reclaim_status TEXT NOT NULL DEFAULT 'linked' CHECK (reclaim_status IN ('linked','reclaimed','skipped','failed')),
    created_by_task UUID NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (plugin_slug, resource_type, resource_id)
);
```

写入点：CreateUserPlugin 代建路径（2.1）、attach-resource CLI、seedPluginVisibility 顺带登记声明型资源。`FlagByKey` 用户插件层优先的既有解析不受影响。

### 2.3 DeleteUserPlugin 回收扩展（`handler/user_plugins.go`）

顺序（软删行 → 回收 → 清理，全程 best-effort + 逐项结果落 ledger）：
1. **活动引用 guard（新增，409）**：存在 `issue.lab_source = flag_key` 且非终态的 issue → 拒绝删除，报数并指引先终态/改绑。（新增一条 `ListActiveIssuesByLabSource` 查询。）
2. 现有：软删插件行 + 摘除内存 flag/registry + 清 visibility + 清 pref。
3. **按 ledger 回收**：
   - `agent` → 归档（沿用 swarm role 归档 `ArchiveSwarmRoleAgentRows` 模式：archived 状态 + `lab_managed` 随 visibility 清除自然解除）；
   - `squad` → 软删；`autopilot` → status 置 disabled；
   - `skill` → **硬删**（skill 表无软删列，DeleteSkill 先例；前提 guard：`agent_skill` 绑定仅指向本插件资源，否则 `skipped` 并在报告中说明，防误删用户复用的技能）；
   - `env_dir` → `~/.multica/plugins/<slug>/` 整目录**移入** `~/.multica/plugins/.trash/<ts>-<slug>/`（不直接 rm；复用 runtime_gc retention ladder 思路，30 天后物理清除——GC sweep 新增分支）。
4. 失败项标 `failed` 留在 ledger；后台 reclaim sweep（挂进现有 runtime_gc ticker）周期重试。
5. 回收结果以 CLI 输出 / API 响应返回逐项清单。

### 2.4 skill 全局注入默认收紧（防"技能污染主列表"）

manifest `capabilities` 增可选字段 `skills_visibility: "global" | "lab_scoped"`：
- **缺省 = 保持现状 global**（append-only 兼容：存量插件 + F-008 ack 语义不变）；
- 新表单/新 CLI `create` 默认写 `lab_scoped`（用户诉求："默认隐藏不注册"）；
- `lab_scoped` 语义：`appendEnabledPluginSkills`（`service/task.go::LoadAgentSkillsForClaim`）跳过该插件；这些 skills 仅注入 (a) `issue.lab_source = 该插件` 的 delegation/leader claim（按 flag_key 匹配）、(b) 该插件 plugin-shell 运行上下文。
- F-008 ack 弹窗仅对 `global` 插件触发。

### 2.5 隐藏默认（确认现状 + 补文档）

代建资源一律即时种 visibility 行 → 不进任何 picker/列表（lab_managed 全 surface 过滤已有法律与测试锚）。"科研实验室/用户插件的智能体不可见不污染"即此机制，无新代码。

### 4.1 委托生命周期评论协议（server，零新端点）

- **开始**：`CreateIssue` 携带 `parent_issue_id + lab_source` 的成功路径（`RecordDelegationEdge` 同一调用点，`handler/issue.go:2804` 邻域）best-effort 发父 issue 系统评论：`[lab delegate] started: <flag_key> → <childKey> (leader <name>)`。AuthorType=system（不触发 mention），格式族与既有 `[lab delegate]` 结果评论一致。

- **结束**：结果评论（CLI 已有）+ child-done 唤醒（已有，含 cancelled 终态）。用户从任一侧终止（4.3）后父 agent 同样被唤醒并在结果评论中看到"取消"语义。

### 4.2 DelegationCard（`packages/views/issues/components/delegation-card.tsx` 新组件）

- **数据**：父 issue 现有 sub-issues 查询中 `lab_source != null` 的子集（不引新端点、不读因果边——列表比边更稳）。
- **渲染**：lab 徽章 + leader + 子 issue 深链 + 状态机（queued/running/done/failed/cancelled，`agentTaskSnapshotOptions` 5s 轮询 = Active Contract #1）+ 终止按钮（复用 `TerminateTaskConfirmDialog` → `api.cancelTask`）。
- **挂载**：issue-detail Sub-issues 区块上方独立 section，仅当存在 lab 子 issue 时渲染（不新增 picker，不触碰 lab_managed 过滤面）。
- **LabProgressCard 补 `user_*` 分支**：现状返回 null → 扩展为 generic 运行状态（复用 snapshot 状态机 + `labRunHref` 深链 plugin-shell）。顺带修复已知残留清单中"不可见 LabPicker chip"（同文件域，机会主义修复）。

### 4.3 终止语义

- 父 issue 卡片终止 = cancel 子 issue 活动任务（现有 `POST /api/issues/{id}/tasks/{taskId}/cancel` 链路：token 吊销 + 5s 轮询中断子进程）。

- leader 代建 instructions 模板补一句边界："只返回结果，不修改父 issue"（内置 lab SKILL.md 已有类似措辞，统一化）。

### 4.4 briefing 措辞升级（delegate_brief.go 渲染函数）

补一行：委托后你将在子任务完成或被取消时被自动唤醒；用户可随时在父/子任一侧终止。命令示例含 `--stage`。（同样纳入五动词 contract test。）

### 5a 因果记忆（随时回忆 / 强调回溯）

1. **`multica causal recall --issue <id> [--depth N]`**（CLI 只读）：GET `/api/causal-graph/subgraph?issue=` 渲染紧凑 markdown。claim 自动注入是 ≤2 跳、16KB 截断的"被动背景"；recall 是 agent 在任务中**主动深化**的通道。
2. **`multica causal trace --issue <id>`**：该 issue 决策链（decision/action/outcome 节点 + causes/depends_on 边 + confidence + provenance），suggested 边明确标注"待确认"。用户评论"回溯/为什么错"时 agent 调用 trace → 定位链路 → 如需修正走 Tier D suggestion（POST 已有端点，自动 ×0.5 置信、never-nag、墓碑）→ 用户在 SuggestedQueue 确认。**回溯=读(trace)+修(suggestion)+人审(confirm)，全部已有端点，零新后端。**
3. **"启用后默认追溯全部任务"**：Tier A 钩子本就全局写入（task enqueue/complete，`Recorder.Enabled()` 按任一用户 pref），无需新代码——把这一行为写进 Labs 设置页 causal_graph 卡片描述与 docs。
4. 单任务决策视图：已存在（IssueCausalGraphIcon + 聚焦全图）。P2 机会主义接线 `useCausalGraphPath`（当前无 UI 消费者）到聚焦图的"追溯路径"高亮。

### 5b LLM 实体/关系抽取（无向量模型的默认 LLM 方案）

- 新 `service/causal_graph/llm_extract.go`：issue 终态（或夜间 evolver 窗口）取该 issue 时间线前 N 条评论 + issue 正文 → `/api/runtime/llm-call`（json_schema：`{entities:[{type,label,description}], relations:[{from,to,type,rationale}]}`，先例 `claude_lab_llm_forecast.go`）→ 映射 causal_node/causal_edge 建议。
- **trust ladder 合规**：一律 Tier D suggested、confidence ≤0.5、provenance `llm_extract`、dedup_key `llm_extract:<issueID>`（每 issue 一次）、FindCausalEdgeBetween any-status 探针、失败静默、flag 门控 `causal_graph`。新 Source 常量同 commit 加入 `experimental.AllSources`（法律：`TestAllSourcesContainsCausalGraph` 先例）。
- 节点类型映射守 CHECK 集（decision|action|outcome|assumption|evidence|constraint）。

### 5c LLM Wiki 配合（检测后）
