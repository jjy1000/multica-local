# MUL-3724 Cherry-Pick — Architecture Review (Local Fork 0.2.96)

## Summary

Upstream MUL-3724 threads `squad_id` through the squad-leader task lifecycle so the daemon claim path can re-inject the briefing when a leader task was enqueued by the comment-mention path (which never sets `issue.assignee_type = "squad"`). The patch is small (1 migration + 2 service signatures + 5 call sites + 1 briefing-gate rewrite + 1 broadcast field) and 100% additive — but **the briefing gate rewrite is the highest-risk item**: it currently has no unit test in `daemon_test.go`, so any silent regression here is invisible to `make test`. Recommend backfilling `squad_id` via a per-claim fallback (read-time, not row-mutate) so in-flight leader tasks from before migration 127 still receive briefing. Bump to 0.2.97 (patch, `apps/desktop/package.json` only). Do NOT repackage desktop in this change.

### 4. Backfill decision

**Recommended**: add a per-claim read-time fallback for pre-existing in-flight leader tasks whose `squad_id IS NULL`. Concretely, in the briefing-gate rewrite at `daemon.go:1387-1441`:

```text
if resp.Agent != nil && task.IsLeaderTask {
    var squad db.Squad
    var ok bool
    if task.SquadID.Valid {
        squad, ok = h.Queries.GetSquadInWorkspace(ctx, GetSquadInWorkspaceParams{ID: task.SquadID, WorkspaceID: issue.WorkspaceID})
    } else {
        // Backfill: pre-migration-127 in-flight tasks. Fall back to the
        // legacy issue.assignee_type='squad' lookup.
        if issue.AssigneeType.Valid && issue.AssigneeType.String == "squad" && issue.AssigneeID.Valid {
            squad, ok = h.Queries.GetSquadInWorkspace(ctx, GetSquadInWorkspaceParams{ID: issue.AssigneeID, WorkspaceID: issue.WorkspaceID})
        }
    }
    if ok && uuidToString(squad.LeaderID) == resp.Agent.ID {
        // … inject briefing …
    }
}
```

**Pros of the per-claim fallback**:
- Zero new migration. The migration only adds the column; no row-mutate backfill needed.
- Self-healing: any pre-existing in-flight leader task picked up by the daemon after upgrade still gets briefing for the lifetime of that task.
- Symmetric to the upstream "defensive gate" — same idea but applied on the read side instead of the write side.
- No risk of grabbing wrong rows: the legacy gate `issue.AssigneeType == "squad"` already had a year of battle-testing as the sole gate.

**Cons**:
- Adds two extra DB roundtrips per claim for the (post-migration) happy path. Mitigate by short-circuiting: only attempt the fallback when `task.SquadID` is invalid.
- Two code paths to reason about during the lifetime of the bug surface window.
- The fallback can't recover the briefing for tasks that claim between the upgrade and the moment the daemon's claim reader picks them up — but the daemon claim path is sub-second, so this window is tiny.

**Pros of "just document the boundary"**:
- Simpler diff, no fallback code to test.
- In single-user local-fork usage, in-flight leader tasks at the moment of an upgrade are almost always zero (only relevant if you upgrade mid-conversation).

**Cons of "just document"**:
- The user-reported bug (`squad leader boots with zero squad context`) is a silent corruption — the agent just silently degrades into doing work itself. If they hit it, they have no signal.
- The bug is exactly the kind of thing a user hits once after upgrading and then blames the upgrade itself.

**Recommendation**: **implement the per-claim fallback.** It's 8 extra lines, the dual code path is bounded by the column being populated by every new enqueue (so the fallback path will be dead within a few claim cycles), and it provides a clean regression-free upgrade story. **Retire the fallback** once a 0.3.0 release makes 0.2.97 unreachable — or document the deprecation as a 1-version sunset.

## Root Cause

The bug is a **gate-input asymmetry** at `daemon.go:1387-1441`. The current gate reads `issue.AssigneeType` to decide whether the briefing should be injected, but the assign-on-comment and comment-mention paths both leave `issue.assignee_type` pointing at the comment's target (the *leader agent* for mentions, the *issue's existing assignee* for assign-on-comment that targets a squad). Only the on-assign path (`service/issue.go:399`) sets `issue.assignee_type = "squad"`, and only that path benefits from the briefing. Comment-mention leader tasks wake the agent but with no briefing, so the leader degrades into doing work itself.

The fix moves the gate input from `issue.AssigneeType` (which is the wrong signal — it describes the issue's static assignee, not the current task's provenance) to `task.IsLeaderTask && task.SquadID` (which describes the task's actual role). `task.IsLeaderTask` is already populated by migration 090 + every `EnqueueTaskForSquadLeader*` call. The new `task.SquadID` column (migration 127) is the missing piece that lets the daemon cross-check that the task is genuinely a leader-role task for a specific squad (and not, e.g., a leader-role task whose squad was deleted).

## Compatibility Notes

- **Additive schema only.** `squad_id` is nullable; existing rows stay valid; no FK constraint added (squad_id is a soft pointer; matching squad existence is checked at claim time).
- **No telemetry, no OAuth, no cloud, no invitations** touched — confirmed by reading every modified file path against the localization-excluded list in `CLAUDE.md`.
- **No frontend / renderer changes** strictly required. `resp.SquadID` is already a `ClaimResponse` field (`agent.go:291`), populated by the quick-create path. Adding it to `agent_task_queue` is purely a backend story; if the renderer needs to display it later, that's a follow-up.
- **API backward compat**: `squad_id` is `omitempty` in the broadcast payload, so old clients ignore it.
- **DB rollback**: `down` migration drops the partial index and the column. No data loss for non-null rows because nothing depends on the column existing at read time (legacy fallback handles the absent case).
