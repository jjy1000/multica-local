# Multica 0.3.15 + 0.3.16 — Claude Science research lab

> Scope, owner, and rollback contract for the research-lab ship.

## TL;DR

User asks for the `claude_science` Labs flag to mount a real
research workspace inside Multica, not a marketing placeholder. When
the flag is on:

1. Multica spawns a **dedicated workspace** (slug `claude-science`)
   whose first-time setup pulls in the bundled OpenScience assets.
2. That workspace ends up with **292 skills + 13 agents + 5 squads
   (4 domain + 1 joint) + 4 MCP servers** (KEGG / Zinc /
   Metabolomics Workbench / USPTO), all tagged as
   `experimental_source='claude_science'`.
3. The Claude Science page (renderer route at
   `/experimental/claude-science`) shows live activity: skill
   usage, MCP call counts, recent issues, recent comments touched
   by research agents.
4. **No agent anywhere in Multica may edit, optimize, or delete any
   tagged resource.** All read paths filter for the owner (human);
   write paths return 423 Locked. The `claude_science` flag is the
   only switch that controls visibility.
5. When the user toggles the flag off, every resource carries the
   tag and stops rendering everywhere (sidebar, settings, agent
   pickers, IPC surfaces). The rows are **soft-hidden** (`hidden=true`
   in the tag table) — they are NOT deleted, so a re-toggle restores
   the workspace content 1:1.
6. Model routing stays on Multica's provider chain (already enforced
   in 0.3.14).

User-confirmed scope (2026-07-13):

- workspace scope: independent workspace
- off-flag behavior: soft hide
- import scope: full 292 skills (rather than a curated subset)
- squad structure: domain-multiple squads + 1 joint squad
- science connectors: real MCP server packaging (5 → 4 after
  deduplication, see PR 8 below)
- view side panel: yes, render recent research activity

Estimated effort: 10 PRs across two minor versions.

## Database schema

Migration `148_claude_science_experimental_lock.up.sql`:

```sql
-- Per-resource experimental lock. Soft hide + 423 on write.
CREATE TABLE experimental_resource_lock (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  experimental_source TEXT NOT NULL
    CHECK (experimental_source IN ('claude_science')),
  resource_type TEXT NOT NULL
    CHECK (resource_type IN
      ('workspace','skill','agent','squad','member','mcp_server')),
  resource_id UUID NOT NULL,
  hidden BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  hidden_at TIMESTAMPTZ,
  UNIQUE(experimental_source, resource_type, resource_id)
);
CREATE INDEX idx_lock_by_source
  ON experimental_resource_lock(experimental_source)
  WHERE hidden = false;
```

A separate `hidden=true` row means "the lab is off; this row should
not surface" — the row is kept so toggling the flag on again does
not have to recreate any of the underlying data. The
`experimental_resource_lock` rows themselves are owned by the
system; user agents and even workspace members cannot write to
this table.

The actual SKILL.md / agent / squad / member rows live in their
existing tables (`skill`, `agent`, `squad`, etc.) untouched —
this migration does NOT move them. It only adds the lock overlay.

## PR 1 — `experimental_resource_lock` table + helper package

**Migration** `148_claude_science_experimental_lock.up.sql` matches
the schema above. Rollback companion deletes the table; CLAUDE.md
"forward-only migrations" rule is honored because the *table* is
new, not modified.

**Helper package** `server/internal/experimental/lock.go`:

```go
package experimental

// Source is the closed enum of experimental surfaces that can attach
// resources. Currently only claude_science. Adding pythia_oracle or
// future labs means appending a constant here.
type Source string

const (
    SourceClaudeScience Source = "claude_science"
)

// ResourceType enumerates the kinds of rows the lock can attach to.
type ResourceType string

const (
    LockWorkspace  ResourceType = "workspace"
    LockSkill      ResourceType = "skill"
    LockAgent      ResourceType = "agent"
    LockSquad      ResourceType = "squad"
    LockMember     ResourceType = "member"
    LockMCPServer  ResourceType = "mcp_server"
)

// Lock is what we hand back from a successful claim. Stored hidden=false.
// Hidden=true rows are still queryable by the system but invisible to user
// reads — see server/internal/handler/skill_filters.go etc.
type Lock struct {
    Source    Source
    ResType   ResourceType
    ResID     pgtype.UUID
    Hidden    bool
    CreatedAt time.Time
    HiddenAt  *time.Time
}

// Claim attaches a lock to (source, type, id). Idempotent. Called by
// the install flow after creating the underlying row.
func Claim(ctx context.Context, q db.Querier, src Source,
    rt ResourceType, id pgtype.UUID) error

// Hide / Restore flip the visibility of every row attached to src.
func Hide(ctx context.Context, q db.Querier, src Source) (int, error)
func Restore(ctx context.Context, q db.Querier, src Source) (int, error)

// IsHidden returns true iff every row of (rt, id) is hidden.
func IsHidden(ctx context.Context, q db.Querier, src Source,
    rt ResourceType, id pgtype.UUID) (bool, error)

// IsLockedErr / WriteWhenLocked are used by handlers to translate
// the policy into HTTP responses.
type ErrLocked struct{ ResourceType string; ID string }
func (e ErrLocked) Error() string
```

The handlers in PR 2 / PR 4 call `experimental.IsHidden` /
`experimental.Lock` on every read/write so the lock policy is one
place, not scattered.

**Tests** mirror the handler convention:
- `claim_idempotent`
- `hide_round_trip_visibility`
- `restore_preserves_row_ids`

**Verification**: `go test -count=1 -race ./internal/experimental/`

## PR 2 — Hidden-tag read filters

Every handler that reads `skill`, `agent`, `squad`, `member`,
`mcp_server` joins the new lock table and filters out hidden
rows. The two natural shapes:

```sql
-- SELECT existing … FROM skill
SELECT s.*
FROM skill s
WHERE s.workspace_id = $1
  AND NOT EXISTS (
    SELECT 1 FROM experimental_resource_lock l
    WHERE l.resource_id = s.id
      AND l.resource_type = 'skill'
      AND l.hidden = true
  )
```

Rather than duplicating the predicate in every handler, the handlers
get a small helper:

```go
// VisibleSkills returns the workspace's skills minus any whose
// claude_science lock is hidden. Used by the skills tab + agent
// picker alike.
func (h *SkillHandler) VisibleSkills(ctx context.Context, wsID pgtype.UUID) ([]Skill, error)
```

`mcp_server` joins are added where the agent-runner reads tools.
The trainer reads (chat input picker, agent member picker, settings
"workspace members" tab) all go through the visible variants.

**Tests** assert:
- before install, returns `[]`
- after install with flag off, returns `[]`
- after install with flag on, returns full list
- after hide, returns `[]` but row still in DB

**Verification**: `go test -count=1 -race ./internal/handler/`

## PR 3 — `/api/experimental-resources` install/rollback endpoints

```
POST /api/experimental-resources/{key}/install
  → runs the lab's install flow once; returns 201 with the install
    manifest (counts of skills, agents, squads, MCP servers, members)
  → idempotent: re-calling on an already-installed lab returns 200
    with the same manifest

POST /api/experimental-resources/{key}/rollback
  → hides every row tagged with {key}
  → returns 204

GET /api/experimental-resources/{key}/status
  → returns:
    {
      "key": "claude_science",
      "installed": true,
      "hidden": false,
      "manifest": { "skills": 292, "agents": 13, "squads": 5,
                    "mcp_servers": 4, "members": 13 }
    }
```

The install is currently the **only** way the workspace `claude-science`
gets created — there is no "create workspace" button for it. Flag
on → installer runs → flag off → rollback hides but never deletes.

Handler signatures live in
`server/internal/handler/experimental_resources.go`.
Sqlc queries in `server/queries/experimental_resources.sql`.

**Verification**: integration test mounts the HTTP, posts the JSON,
asserts DB rows.

## PR 4 — Wire install/rollback to flag toggles

`server/internal/handler/experimental_flags.go:PatchExperimentalFlag`
calls into the experimental_resources install/rollback handlers
when the key in question has been previously declared installable:

```go
type installableKey struct{ key string; handler Installer }

var installables = map[string]installableKey{
    "claude_science": { key: "claude_science", handler: installClaudeScience },
}
```

If user flips `claude_science` from off → on, the PATCH handler
runs the installer idempotently, sets hidden=false on every tagged
row. If the user flips it off, hidden=true.

The HTTP response shape (`ExperimentalFlagResponse`) gains an
optional `installation` field with the manifest so the Labs UI can
render "已装载 292 skills" instead of just "已启用" without a
second round-trip.

**Verification**: integration test for flag PATCH installs and
hides on each direction.

## PR 6 — Dedicated `claude-science` workspace creation

`installClaudeScience` runs as:

1. Create workspace `claude-science` if missing (CLAUDE.md: a
   reserved slug, see schema).
2. Create `member` rows for the 13 agents with admin role.
3. Create `skill` rows for all 292 skills.
4. Create `agent` rows for all 13 agents with the OpenScience
   prompts as `system_prompt` field (the Multica `agent` table
   already has this column; verified in
   `server/migrations/001_init.up.sql:36`).
5. Create the 4 domain squads + 1 joint squad, attaching the
   relevant agents as members.
6. Drop a lock row for every resource created above.

The installer is idempotent: it inspects the existing state and
only writes what's missing. Re-running on an already-installed lab
returns the same manifest.

**Workspace slug**: `claude-science` is added to
`server/internal/handler/reserved_slugs.json`. The TS side regenerates
via `pnpm generate:reserved-slugs`. The renderer page moves under
that workspace prefix once flag-on, OR stays pre-workspace under
`/experimental/claude-science` with a layout that filters by
`workspace_slug == "claude-science"` (chosen for parity with
`/experimental/pythia` pre-workspace; a separate workspace context
view is reserved for a future ship).

**Verification**: integration test
`TestExperimentalResourcesInstall_RoundTrip` covers install →
hide → restore → re-hide.

## PR 8 — 4 MCP servers (KEGG / Zinc / Metabolomics / USPTO)

`apps/desktop/vendor/mcp-servers/{kegg,zinc,metabolomics,uspto}/`
hosts the 4 servers. Each is a thin Node 20 standalone binary
(`@modelcontextprotocol/server-stdio` baseline, with the lab's
specific tool surface).

Roughly:

```js
// apps/desktop/vendor/mcp-servers/kegg/src/index.js
import { Server } from "@modelcontextprotocol/sdk/server/stdio.js";

const server = new Server({ name: "kegg", version: "0.1.0" }, {
  capabilities: { tools: {} }
});

server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [
    {
      name: "kegg_get_pathway",
      description: "Fetch a KEGG pathway record by ID (e.g. hsa00010).",
      inputSchema: { type: "object", properties: { id: { type: "string" } } }
    },
    …
  ]
}));

server.setRequestHandler(CallToolRequestSchema, async (req) => {
  if (req.params.name === "kegg_get_pathway") {
    const id = req.params.arguments.id;
    const url = `https://rest.kegg.jp/get/${id}`;
    const text = await (await fetch(url)).text();
    return { content: [{ type: "text", text }] };
  }
});

await server.connect(new StdioServerTransport());
```

`setup-claude-science.sh` ships a `node_modules` install step for
each server. `bundle-cli.mjs` builds each server with Bun (cheaper
than Node for single-binary outputs) and copies the result into
`apps/desktop/resources/mcp-servers/`. Bundle size impact
≈40 MB total (each server ~10 MB native binary).

Zinc / Metabolomics / USPTO follow the same shape, swapping the
adapter for each database's REST API.

The install flow attaches `mcp_server` resource lock rows
matching `SourceClaudeScience`. The renderer side panel reads from
`MCPCallStats` (added in PR 9) to surface usage.

**Verification**: typecheck + manual launch via
`bun apps/desktop/vendor/mcp-servers/kegg/src/index.js` against
the OpenAI SDK test harness.

## Implementation order

Single linear sequence. The user already approved scopes for 0.3.15
and 0.3.16; implementation will follow PR # one at a time with the
existing CLAUDE.md "narrowest useful checks" rule applied — no
broader verification except the smoke + row-parity at the end.

For full clarity with the user: **this is a 2-version ship**. 0.3.15
ships the lab without MCP servers; 0.3.16 ships MCP. A single 0.3.15
shipping MCP would either delay or dramatically bloat PRs — both
worse than the explicit two-version split.
