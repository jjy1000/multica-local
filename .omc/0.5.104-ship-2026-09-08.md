四件用户实测驱动的修复(fix commit `97b76aa8f`),全部根因定位自 9/8 上午的 live 日志 + DB 证据
(测试 issue「模拟推演方案」`592ecbaf`)。发版前 `pnpm typecheck` 全绿、
`go test ./internal/... ./pkg/agent/...` 41 包全绿、views vitest 1849 通过。

## 1. 引擎 env 注入选错 profile — 推演从未真正调用 LLM(真根因)

**症状**:推演跑完落库,报告标「来源:真实引擎推演」,但耗时异常
(10 轮 45.047s ≈ 纯轮间隔 9×5s;1 轮仅 16.8ms),服务器日志
`/api/runtime/llm-call` 桥接调用**历史为 0**。

**证据**:落库 envelope 的 narrative 是引擎内部兜底占位文本
(「(推演第 1 轮,种子 …)…的演化路径仍在收集中。」)却被 Go 侧标为
`oracle`;10 轮 run 里 8 轮 `oracle`(假)+ 2 轮 `synthetic_oracle_failover`。
引擎进程(PID 17593)`ps eww` 实测环境只有 `MULTICA_REQUIRED=1`,
**缺 `MULTICA_AGENT_RUNTIME_URL` / `MULTICA_API_TOKEN`** →
`oracle._complete` 每次调用立即 RuntimeError → 引擎 catch 后返回
占位文本 + HTTP 200 → Go `queryOracleIssue` 只看 HTTP 状态码标 `oracle`。

**根因**:`pythiaRuntimeEnv`(apps/desktop/src/main/pythia-manager.ts)
只取 readdir 顺序**第一个** `desktop-*` profile 且失败后不再尝试 ——
字母序第一是遗留云配置 `desktop-api.multica.ai`(有 config.json 但无
token),`if (!apiUrl || !token) continue` 跳出循环,真正有 token 的
`desktop-localhost-8090` 永远不会被尝试。

**修复**:
- daemon-manager.ts 新增导出 `activeDesktopProfileName()`(由
  `targetApiBaseUrl` 经 `deriveProfileName` 推导,与 daemon/syncToken
  同源),pythia-manager 优先使用;兜底扫描改为**全量候选逐一校验**
  (desktop-* 优先),第一个同时有 server_url+token 的胜出。
- 0.5.103 的引擎自动启动让引擎常驻,把这个老 bug 从「synthetic 占位」
  恶化成「oracle 标签的假推演」——诚实法则(honesty law,0.5.82)在
  Go/引擎边界被击穿。

## 2. 诚实法则补洞:引擎兜底必须自我声明

- 引擎 `server.py /forecast/issue`(vendor/pythia-src,打包时 bundle-cli
  从 vendor 重拷):`what_if` 抛错**或**解析不出 predictions 时,响应带
  `synthetic: true`。
- Go `queryOracleIssue` 解析该字段,为真时 envelope 改标
  `synthetic_oracle_failover` → 报告「数据来源」显示「引擎失败后本地
  回退」、面板渲染「模拟数据」徽标,占位数据不再冒充真实推演。
- 回归:`TestQueryOracleIssueSyntheticRelabel`(httptest 双分支)。

## 3. 轮次可控:默认 3 轮 + 问题文本指定轮数

- 服务端 `defaultIssueForecastRounds` 10 → 3(0.3.30.3 的「10 轮契约」
  退役;延迟 ~45s→~15s,LLM 调用 10→3 次/issue),硬上限仍 10。
- 新 `packages/views/issues/utils/forecast-rounds.ts`:解析标题/正文中
  「推演N轮 / N轮推演 / 预测|模拟|预演 + N轮」短语(title 优先,首个
  匹配胜出,钳位 1..10)。**刻意收紧邻接**:「分3轮讨论」「第一轮」不会
  误触发。`resolveForecastRounds(title, body)` 供两处触发点使用。
- create-issue 与 use-issue-actions 的 `rounds: 10` 硬编码全部替换;
  创建流程改为 fire-and-forget(不再 await 整个 SSE 卡提交最长 45s)。
- 回归:`forecast-rounds.test.ts` 11 用例 +
  `use-issue-actions.test.tsx` 默认 3 轮 + 「推演5轮→5」两断言。

## 4. 推演可终止:共享取消注册表 + 面板停止按钮

- 新 `packages/views/issues/utils/pythia-forecast-trigger.ts`:模块级
  AbortController 注册表(每 workspace+issue 至多一个在跑;新触发顶掉
  旧运行,防双份 SSE 叠跑双倍烧轮次+双份报告评论)。
- create-issue / use-issue-actions / PythiaPanel 三条触发路径全部接入;
  PythiaPanel「推演中」卡片加 ⏹ 停止按钮(i18n ×4)。
- 服务端 SSE 轮循环本就监听 `r.Context().Done()`(forecast_issue.go
  轮间 select),断开后已跑轮次经 deferred persist 照常落库 —— 前端
  abort 即全链路生效,部分结果保留。
- 注:0.5.103 IssueLabsSection 的停止按钮只覆盖 agent-task 型实验室,
  pythia 推演是纯 SSE(AutoDispatch=false 无任务行),本修复补上该缺口。

## 5. 旗标关闭诚实状态(当日 13:08 事故直接产物)

**症状**:用户遇「推演未在 90 秒内返回结果…点重试」stuck 面板,实际
引擎活着。真因:`experimental_pref` 表中 pythia_oracle 行消失
(11:30 批量 PATCH 曾生效为 200,12:08 后 404;无 API DELETE 痕迹,
删除手法未定罪;causal_graph 行同样消失)→ 守卫 `RequireExperimentalFlag`
按 `DefaultVal=false` 每请求 404 推演全部端点 → runs 404 被客户端当
「无结果」+ 旧触发戳 → stuck 文案误导为引擎宕机,重试按钮静默 404。
(已用桌面 token PATCH 恢复 enabled=true;遇同类 404 先查 pref 表。)

**修复**:

  「Pythia 实验室已停用 + 开启指引」(`pythia_flag_off*` i18n ×4),
  不再进入 stuck/retry 分支。
- LabProgressCard pythia 变体:旗标 off 时 runs 404 渲染 muted idle 行,
  不再显示红色 failed。
- 回归:`lab-output-panel.test.tsx` 旗标 off 用例(断言 stuck 面板与
  retry 按钮均不出现)。
