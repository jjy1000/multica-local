# Multica 0.3.11 — 2026-07-13

## Summary

Ships the vendored OpenScience single-binary so the `claude_science`
Labs flag finally becomes end-to-end usable. The flag was wired in
0.3.8, the spawn-safety fix landed in 0.3.10, and this release
completes the bundle so the user does not have to manage the
upstream repo themselves.

## What's new

### Vendored OpenScience binary (147 MB)

`apps/desktop/scripts/setup-claude-science.sh` builds the upstream
OpenScience (`/Users/jiangjianyan/Downloads/openscience-main`) Bun +
Vite monorepo into a single-binary via `bun run build -- --single`
and stages it at `apps/desktop/vendor/openscience-bin/openscience`.
`bundle-cli.mjs` then copies it to
`apps/desktop/resources/openscience/openscience` and the
electron-builder `asarUnpack` rule ships it inside
`Multica.app/Contents/Resources/app.asar.unpacked/resources/openscience/openscience`.

The `setup-claude-science.sh` script handles the upstream quirks:

- The upstream repo is not a git checkout (it lives in `~/Downloads/`),
  but `backend/cli/script/build.ts` calls `git branch --show-current`
  to derive the channel name. The script initializes a local git
  repo so the build does not crash on the missing `.git`.
- The upstream binary carries an Apple Developer ID signature that
  blocks ad-hoc re-signing. The script runs `codesign
  --remove-signature` first so ad-hoc signing succeeds.
- `xattr -cr` strips the Gatekeeper quarantine that the
  `~/Downloads/` origin attaches to the binary.

### Richer error reporting (renderer)

`claude-science-view.tsx::humanizeBootError` now distinguishes three
failure modes:

| `error.code` | User sees |
|---|---|
| `BINARY_NOT_BUNDLED` | "运行 `bash apps/desktop/scripts/setup-claude-science.sh` 然后重打 DMG" |
| `SERVICE_NEEDS_SETUP` | "在终端先跑 `openscience login` 或 `openscience keys add` 再回 Multica" |
| (other) | Raw main-process message |

The middle case is the new one — when the bundled binary launches
but does not become healthy in `readyTimeoutMs` (default 30s, Claude
Science 60s), the manager now wraps the timeout error with
`code = "SERVICE_NEEDS_SETUP"` and a message that points the user at
OpenScience's first-run onboarding flow. That flow lives outside
Multica by design — model routing stays on OpenScience, not Multica's
provider chain (memory: `multica-0.3.8-experimental-services-2026-07-13.md`).

### Manager template contract update

`BaseExperimentalManager.start()` adds the structured
`SERVICE_NEEDS_SETUP` error code in the catch block. This makes the
contract symmetric with `BINARY_NOT_BUNDLED`: every renderer for a
Labs-gated service can pattern-match on the code and produce
actionable copy.

## User-visible change

Before 0.3.11: enabling `claude_science` rendered
"Claude Science unavailable / service not bundled" because the
OpenScience binary had never been built or staged.

After 0.3.11: enabling `claude_science` and clicking the sidebar
entry spawns the OpenScience binary. The first time, the binary
needs external setup:

```
/Applications/Multica.app/Contents/Resources/app.asar.unpacked/
  resources/openscience/openscience login
# or
.../openscience keys add
```

The renderer surfaces that exact command via the
`SERVICE_NEEDS_SETUP` code path. Once OpenScience is configured on
the host, subsequent Multica cold-starts pick up the existing config
and the iframe renders the SolidJS workspace.

## Known caveats

- DMG hand-built via `create-dmg` (memory 0.3.4 workaround).
- DMG size **357 MB** (up from 228 MB). The +129 MB is the
  OpenScience Bun-compiled native binary. Future releases that
  also vendor Pythia (`pythia_oracle`) will add another ~50-100 MB.
- OpenScience needs network access on first launch to fetch
  `models.dev/api.json` and sync the provider whitelist. Offline
  first-launch will hang at the SYNC_BUDGET_MS cap and surface
  `SERVICE_NEEDS_SETUP`.
- Pythia (`pythia_oracle`) is **still** not vendored — its setup
  script (`setup-pythia.sh`) is not yet written because the user
  asked about Claude Science first. Same pattern, same caveat.
