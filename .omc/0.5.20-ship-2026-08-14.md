## Risk vs outcome

- Risk: The new `agentEnv["TMPDIR"]` overrides any
  `custom_env`-supplied value; if a user plugin was relying on
  setting its own TMPDIR for a sub-tool it spawns, that path is now
  the daemon's per-task private dir. Mitigated: the daemon's value
  is itself a writable, freshly-mkdir'd dir, so any sub-tool that
  respects TMPDIR gets a usable scratch space (and one that's owned
  by the task, not shared across siblings — strictly safer).
- Outcome: 0 regression in ship gate, 3 new tests pin the contract.

## Audit + hardening (47b104b2f)

Post-ship audit found 2 MEDIUM + 2 LOW findings, all closed in a
follow-up commit:

- **MEDIUM #1**: `os.Chmod(root, 0o700)` clobbered user-provided
  override base permissions (e.g. a self-hoster pointing at a
  shared 0o755 CI tmp dir would silently lose sibling read access).
  Fix: track `rootCreated` (true only when daemon owns the dir via
  MkdirAll); skip Chmod on override paths.
- **MEDIUM #2**: `MULTICA_AGENT_TEMP_BASE` length not validated
  against the AF_UNIX sun_path cap (104B macOS / 108B Linux).
  Long override silently re-introduced the original "AF_UNIX path
  too long" failure the patch closes. Fix: extract shared
  `afUnixSunPathCap=104` + `afUnixSunPathSuffixReserve=40`
  constants (used by test + docs); reject
  `len(dir)+reserve >= cap` with clear error.
- **LOW #3**: fixed `.multica-writeprobe` filename raced between
  parallel `ensureTaskTempDir` calls. Switched to
  `os.CreateTemp(base, ".multica-writeprobe-*")` for unique probe
  names per call.
- **LOW #4**: bare `MkdirAll`/`Chmod` error returns. Wrapped with
  `fmt.Errorf("create private temp root %q: %w", root, err)` etc.
  so permission-denied failures name the path that failed.

Test hardening:
- `TestRunTask_InjectsPrivateTaskTempDir`: drops `t.Parallel`
  (incompatible with new `t.Setenv` env isolation hardening) +
  uses shared cap constant instead of magic 64.
- `TestRunTask_TaskTempBaseOverride`: switches to short
  `/tmp/multica-test-*` override base (macOS `t.TempDir` is too
  long for the cap; matches real-world override shape) +
  `t.Cleanup` resets `MULTICA_AGENT_TEMP_BASE` to "" so sibling
  tests see clean env.
- `TestRunTask_TaskTempBaseInvalidFailsStartup`: adds
  `too-long_path_rejected` subtest pinning MEDIUM #2 fix.

## Lessons

- **The bug surfaces as "sub-agent interrupt" — but the
  distribution of the symptom (silent no-enqueue from the server
  side vs fast-fail from the daemon side) hid two distinct bugs**.
  Bug A: server-side `@mention` dedup silently eating 2nd+ mentions
  on same issue thread (`agent_task_queue_coalesced_comment_ids`) —
  separate workstream, deferred. Bug B: this fix. Don't conflate.
- **`taskTempDirPath` must honor `MULTICA_AGENT_TEMP_BASE`** or the
  helper returns a path under `/tmp/multica-<uid>` while
  `ensureTaskTempDir` actually creates it under the override — the
  test surfaced this on first run; one-line fix to keep them
  consistent. Document the invariant in the comment block.
- **`t.Setenv` and `t.Parallel()` are mutually exclusive** — even
  in subtests. Both `TestRunTask_TaskTempBaseOverride` and
  `TestRunTask_TaskTempBaseInvalidFailsStartup` lost their
  `t.Parallel()` markers for this reason; the tests still cover
  the contract because they exercise env-var setup that must be
  sequential.
- **Re-applying an upstream PR without first reading its diff is
  exactly the failure mode the previous session hit**. PR #6481 was
  docs-only in this fork's cherry-pick context; the actual code
  change lives in #5116. Reading the diffs directly (via
  `ctx_fetch_and_index` of the `.diff` URL) before applying saved a
  half-day of archeology vs the previous session's "revert + reapply
  guess" loop.
