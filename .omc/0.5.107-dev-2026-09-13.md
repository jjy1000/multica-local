# 0.5.107 开发记录 — 实验室环境 + 实验室插件链路审计修复批（2026-09-13）

> **状态：未提交、未打包、未发版。** 本轮只做「审计 → 复核 → 修复 → 门禁」。`apps/desktop/package.json` 仍为 **0.5.106**（唯一可改版本号，见 `.omc/version-anchor.md`），`/Applications/Multica.app` 实测也是 0.5.106。0.5.107 只是本轮代码注释与本文档使用的**目标批次号**，尚未成为已发布版本。

## 一句话

对 labs 两条链路（内置实验室沙盒 + `user_*` 插件）做端到端审计，确认 8 处真实缺陷并全部修复：其中 **1 个密钥泄漏面**（沙盒 python 子进程继承服务端全量环境）、**1 个用户可见的功能失效**（Labs 开关点了弹回）、**1 个「关 flag 不关执行」**、**1 个 batch 层静默持久化矛盾数据**（同型缺陷第 3 次复发），其余为产物端点加固对齐、死代码清理与过期文档修正。

## 审计方法与三条撤销

三个并行取证代理（沙盒 runtime / 插件生命周期 / 跨层契约与测试真实性）+ 主线逐条 `path:line` 复核。**复核后撤销了 3 条代理结论**，记录在此以免下轮重复误判：

| 代理结论 | 复核结果 |
|---|---|
| `?sig=` 在 Auth 组外跳过鉴权，`uid` 从不与实际用户比对 → 潜在越权 | **撤销**。HMAC 明文覆盖 `uid\|slug\|artifactID\|exp` 全元组（`handler/plugin_artifact_sign.go` 的 `pluginArtifactSignMessage`），5 分钟 TTL、每进程随机密钥、`ConstantTimeCompare`、过期先判。签名即能力，无法伪造。 |
| `llm_wiki_bridge` 的 RuntimeKind 在 catalog / manifest / 桌面描述符三处不一致 = 缺陷 | **撤销**。`experimental/catalog.go` 该条注释明写有意分裂：服务端 chi adapter 在进程内 = `inline`，桌面 manager 单独管 stdio MCP 生命周期 = `subprocess`。仅剩「无 manifest↔catalog parity 测试」。 |
| `FLAG_ROUTE_SUFFIX` 只有 8 行 vs catalog 10 个 key = 契约违反 | **撤销**。缺的两行有退役注释交代（`chat_pin_ui` 0.3.68 死链移除、`swarm_topology` 0.5.105 随运行时退役移除），测试同时钉了 8 键全集与未知键负例。仅剩 `user_*` → `plugin/<slug>` 映射无测试。 |

另外两处**定性被下调**（现象真、危害被高估）：产物 `text/html` 内联直出不是可利用的存储型 XSS（打包态 renderer 在 `file://`、产物端点在 `:8090`，不同 origin，且 `experimental-artifact-view.tsx` 走 `rawRequest` + blob URL + `lab-attachment-sanitize`）；`POST /api/user-plugins/{slug}/run` 不受闸也不是「远端命令执行」（单人本地 fork、manifest 由用户自建），真实问题是**违反仓库自己的 flag-off 绕开规则**。

## 修复清单

### 1. E1 — 沙盒子进程环境净化（最高优先）

`handler/claude_science_runtime.go` 的 execute 从未设 `cmd.Env`，Go 语义下 nil Env **静默继承 `os.Environ()`**。同仓 `user_plugin_runtime.go::pluginRuntimeEnv` 的注释早就写明了这个攻击面（恶意 entry.py 可通过 `HOME` → `~/.multica/profiles/<name>/config.json` 读用户 JWT，或复用 `MULTICA_API_TOKEN` 打特权端点）——**实验室沙盒正是那条未加固的兄弟路径**。

- 新增 `runtimeSessionEnv(sessionDir)`：`PATH` + `HOME` 钉到会话目录 + `LANG`/`LC_ALL=C.UTF-8`，不带 `MULTICA_PLUGIN_*`（那是插件运行时的文档化回调契约）；**刻意不覆盖 `TMPDIR`**，否则解释器临时文件会落在会话目录被当成幽灵产物摄入。
- 文件头 Hard constraints 增补 1a 条说明该边界。
- 测试 `TestClaudeScienceRuntime_ExecEnvIsSanitized`：正向对照（哨兵变量确在父进程 env 且子进程确实打印了 `KEYS=`）+ 精确断言白名单集合 + `HOME` 锚定 + 产物响应头。

**确证过程**：临时撤掉那一行重跑，snippet 实际读到 `DATABASE_URL`、`ANTHROPIC_BASE_URL`、真实 `HOME=/Users/...`。故该项从「推断」升级为「实测」。

### 2. P-1 — Labs 插件开关点了弹回（用户可见）

`settings/components/user-plugins-section.tsx` 的 Switch 绑 `plugin.status === "active"`，而 `doToggle` 写的是 `experimental_pref`（`PATCH /api/experimental-flags/{key}`）。两套状态无耦合——`user_plugin.sql` 里 `status` 只被 plugin Update/Delete 改，flag PATCH 从不触碰——所以点击后 refetch 必然弹回，且**关着的 lab 显示为开**。`experimental/components/plugin-shell-view.tsx` 的 SettingsTab 同一缺陷。

- 两处改绑真实状态源：section 用 `useExperimentalFlags()` + `labEnabled()`（显式 `=== true`，缺 flag 行按关处理），shell 用 `useExperimentalFlag(plugin.flag_key)`。
- 测试新增 3 例，其中「行 active + 偏好 off 必须渲染为关」即判别式（旧绑定在此场景必红），故无需真的回滚代码来验证测试有效性。

### 3. P-2 — 关 flag 仍能执行插件代码

`RunUserPlugin` 原先只查 `plugin.Status == "active"`；新建插件行 `status` 直接是 `active`，而其 flag 默认 `DefaultVal:false`，于是 Labs 里关着的插件照样能跑 `manifest.runtime.command` / `entry.py`。

- 补 `experimentalFlagEnabled(ctx, h.Queries, userID, plugin.FlagKey)` 闸（复用 guard 的解析顺序：黑名单 → pref → catalog 默认）。
- 返回 **409 而非 guard 的 404**：该路由刻意可枚举（CRUD 组明确不受闸），调用方已确知插件存在，给 remedy 比假装端点不存在更有用且不额外泄漏。此判断已写进 `cmd/server/router.go` 注释，并把「CRUD 不受闸」限定为**仅管理操作**。
- 顺带修 router 里 `subprocess → 501` 的过期注释（0.5.18 起 subprocess 已可执行）。
- 测试 `TestRunUserPluginRejectedWhenLabDisabled` 是 `/run` 的**第一个 HTTP 层测试**（既有 runtime 测试全为 helper 级、绕开状态判定），含正向对照（开 flag 后同一请求 200 且 stdout 回来）。

### 4. C-1 — batch 层 lab↔assignee 锁缺口（同型缺陷第 3 次）

`handler/issue.go` 的 `BatchUpdateIssues` 只硬编码 `mythos_swarm` + `swarm_topology` 两个 case，而单条路径自 0.5.86 起走 `assigneeLabLockError`（覆盖 `claude_science_lab` / `pythia_oracle` / `semantica` / `timesfm` + `interaction_model=assignee` 的 `user_*`）。批次**显式携带 `assignee_*`** 时，0.3.47 的 leader 自动改写刻意让位（显式 assignee 视为用户选择），于是矛盾数据静默持久化，而单条 PATCH 400。

讽刺的是该 switch 下方的注释正好记录了 0.5.60 audit P0-1 的同型事故（0.5.21 swarm 扩展只落在 Create/Update/UI，没进 batch）。

- 新增检查调用 `assigneeLabLockError`，violation 按 batch 契约 `continue` per-issue；**不加任何新 key**。
- 范围严格限定在「批次显式带 `assignee_*`」，以免改动 0.3.47 自动改写路径（`TestBatchUpdateIssuesLabSourceAutoAssignsLeader` 与 mythos 的三个既有子测均保持不变并全绿）。
- 测试 `TestBatchUpdateIssuesLabAssigneeLockParity` **从 catalog 派生键集合**（非硬编码清单），并对每个键先断言单条路径确实 400（前置条件），再断言 batch 必须 skip。先跑为 4/4 FAIL（batch 持久化），修后 4/4 PASS。

### 5. E4 + E3 — 产物摄入上限与内联直出

- `ingestSessionArtifacts` 原先 `os.ReadFile` 整文件进内存算 sha256，snippet 可用一次大文件写入拖垮 server。改为先 `e.Info()` 取大小，超 `maxRuntimeArtifactBytes`（32 MiB）记 Warn 后跳过（与未知扩展名同一处理路径）。
- 产物字节端点补 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`，对齐同仓 0.5.18 F-006 在插件产物路径已做的加固；文件名走 `filepath.Base` + `%q` 转义（防头部注入）。已核实三类前端消费方（blob URL、`r.text()`）都不读该头，故内联预览不受影响。

### 6. E5 + E6 — 安全网半断与死代码

- `experimental.SetPanicFlagContext` **零生产者**，而 `cmd/server/main.go` 的 recover 哨兵在消费它 → `ReasonPanic` 永不落黑名单，0.3.18 自动禁用只对 5xx burst（`ExperimentalFlagBurst` → `MarkBroken`）真实生效。接线到唯一按-flag 派发点 `Registry.RunInstall`（`WithPanicFlagContext(flagKey, "registry.RunInstall", …)`）。测试 `TestRegistry_RunInstallAttributesPanic`，**故意不加 `t.Parallel`**：它写的是包级全局槽位，顺序组一定早于暂停的并行组完成，且 `TestPopEmptyReturnsFalse` 这类槽位敏感测试才不会与新接线竞争。
- 删 `ScanUserPluginDir`（生产零调用，插件唯一权威来源是 `user_plugin` 表 + boot/CRUD 增量注册）、其 2 个测试、仅供它们的 `writePlugin`/`keysOf`，以及随之失效的 `os`/`path/filepath` 导入。
- 修 `experimental/catalog.go` 中「user plugins 从 `~/.multica/plugins/` 磁盘发现」这句与实现不符的注释。
- 按仓库规则未留「已删除代码」墓碑注释。

### 7. C-2 — 过期文档契约（含镜像同步）

- `server/CLAUDE.md` §Labs：mutex 条目从「`mythos_swarm` ONLY」重写为按 `interaction_model` 判定（列出现今集合、auxiliary/未分类不锁、权威符号名、0.5.107 batch 修复与「不要再加 key」的告诫）；报错文案指引改为可 grep 的真实前缀（旧的 `"mutually exclusive"` 字符串已不存在）。
- 新增跨切规则：**handler 里任何 `exec` 子进程必须显式设 `cmd.Env`**，并列出两个白名单构造器与 `TMPDIR` 例外理由。

## 已知残留（本轮刻意未做，下一批的输入）

1. **batch 的第二类分歧（未修）**：批次只翻 `lab_source`、目标 lab 是 assignee 型、且其 leader agent **未安装**时，0.3.47 改写记 Info 后仍持久化 `lab_source` + 原本人工 assignee —— 正是单条路径 case-2 明令 400 的状态。修它会改变已钉行为，需单独决策。
2. **teardown 账本只写不读（未修）**：`DeleteUserPlugin` 顺序为 soft-delete → 清 visibility → reclaim，非事务逐行提交。若在清 visibility 后、reclaim 前进程死亡，插件已消失而 provision 的 agent/skill 存活**且不再被隐藏**。`migrations/284` 的 `idx_user_plugin_resource_unreclaimed` 无任何查询使用，boot 无 sweeper，唯一恢复是人工 `POST /reclaim`（代码自陈 best-effort，属已知设计而非疏漏）。
3. **`user_*` 路由映射无测试**：`labSourceRouteSuffix` 对 `user_` 前缀的分支（`issue-labs-section.tsx`）零覆盖；`plugin-shell-view.tsx` 的 `parseTabs` 与 `packages/core/api/client.ts` 的 6 个 user-plugin 端点仍是裸 `as T`，违反仓库 API 兼容规则。
4. **`experimental.RunWithTimeout` 仍为死代码**：包内不存在「每-flag init hook 注册表」，接它等于新造功能，故按「不新建功能」的既定范围保留原状（其 `ReasonInitTimeout` 生产者不可达）。
5. **测试面结构性弱点**：lab 端点测试基本绕开 chi 路由表与 Auth 中间件直调 handler（`newRequest` 手工塞 `X-User-ID`），所以「闸口漏挂」这类缺陷在测试结构上不可能被发现；`handler_test.go` 的 TestMain 在 DB 不可达时 `os.Exit(0)`（`scripts/check.sh` 已硬拦，但根 `CLAUDE.md` 的 ship-gate 命令本身不含该前置，照抄即空转绿灯）。
6. **仓库整体 `gofmt -l` 在 HEAD 上就列约 90 个文件**（含大量未触碰文件），说明 gofmt 实际不是既有门禁；本轮只保证自己碰过的文件干净。
7. **一次未复现的 FAIL**：首轮完整 Go 套件出现过 1 次 `internal/handler` FAIL，此后 6 次（含定向与重复全量）均绿；当时输出被我的 grep 过滤器吞掉，未能留下失败测试名，不排除是已记录的共享 `testRuntimeID` 行竞态（`TestQuickCreateIssueParentTrustBoundary`）。
