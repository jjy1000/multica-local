1. 结论与判断

核心判断：可行，但需要精确定义"沙盒"的边界。

你的愿景本质上是把 Labs 从「开发者测试开关」升级为「用户可操作的插件创建 + 运行 + 协同平台」。现有 manifest → catalog → registry → IPC → proxy 链路为此提供了约 70% 的基础设施。剩余 30% 集中在三个点：

  • 动态注册：Catalog 从编译时常量变为「内置 + 用户」双层结构
  • 通用 UI Shell：从一对一手写 React 视图变为 manifest 驱动的标准化面板
  • 创建流水线：用户/智能体通过低代码交互生成完整的插件包（manifest + 资源 + 可选二进制）

关键约束：这不是一个"插件市场"——是单用户本地沙盒。安全模型、分发模型、版本兼容的复杂度因此降低一个数量级。最大的技术风险不是安全，而是前端动态 UI 的复杂度控制。

从你描述的两个典型场景（智能体自优化 vs 科研实验室）中提炼出的核心分类：

2.2 两种运行模式（关键设计决策）

🔄 自驱模式 (Self-Driven)

启用即运行，无需绑定 issue。用户只在 Labs 面板查看历史/状态。

  • 典型：agent_self_optimization、llm_wiki_bridge
  • manifest 标记："trigger": "auto"
  • LabPicker 中隐藏（HideFromIssueLabPicker: true）
  • 无 lab ↔ assignee 互斥
  • 生命周期：enable → 后台调度 → 历史面板 → disable

现有支持：已完整 — HideFromIssueLabPicker + autopilot scheduler skip 已覆盖

📋 任务绑定模式 (Issue-Bound)

在 issue 面板选择启用，绑定后实验室接管任务执行流。

  • 典型：claude_science_lab、mythos_swarm
  • manifest 标记："trigger": "issue_select"
  • LabPicker 中可选，触发 lab ↔ assignee 互斥
  • 可创建实验智能体、调用技能、虚拟实验、交付成果
  • 生命周期：issue 选择 → 创建资源 → 执行 → 交付 → 归档

现有支持：已完整 — issue.lab_source + lab_mode + mutex 三层已覆盖

2.3 协同模型

你描述的「与用户具体智能体/团队协同交互，但相对隔离」映射到现有架构：

用户工作区 → issue.lab_source 绑定 → 实验室接管 roster → experimental_resource_lock 隔离 → visibility 表控制可见性 → 成果回写 issue

这个模型已在 mythos_swarm 的 enhancer 模式中验证：实验室规划 + 用户指定的执行者 + 监督循环。无需新建协同协议，只需将 enhancer 模式泛化为所有任务绑定型插件的标准能力。

4. Gap 分析：从 Labs 到沙盒实验场

4.1 需要推翻/修改的硬约束

硬约束 #2：Users cannot create flags

catalog.go 第 8 行："Users cannot add/edit/delete flags at runtime. New flags land here as a code change."

建议修改为：「内置 flag 不可运行时修改；用户插件 flag 走独立命名空间 user_<slug>，存储在 user_plugin 表中，启动时动态合并到 Registry。」

影响面：IsKnownKey()、DefaultFor()、AllFlagKeys()、NewRegistry() 四处需感知双层结构。

硬约束 #4：Not a plugin system

catalog.go 第 14 行："These are toggle points, not a plugin system."

建议修改为：「内置 flag 是 toggle points；用户创建的 user_* flag 是完整插件，拥有独立 manifest、资源、可选运行时和 UI surface。」

5. 分阶段技术设计

Phase 0 · 前置准备（1 周）

双层 Catalog + 用户插件命名空间

最小化改动，为后续所有阶段打地基。

// catalog.go 改造草案

// BuiltinCatalog 保持现有 var Catalog = []Flag{...} 不变
// 新增：
var userPluginsMu sync.RWMutex
var userPlugins []Flag  // 从 DB/文件系统加载

func IsKnownKey(key string) bool {
    if isBuiltinKey(key) { return true }
    userPluginsMu.RLock()
    defer userPluginsMu.RUnlock()
    for _, f := range userPlugins {
        if f.Key == key { return true }
    }
    return false
}

// NewRegistry() 之后：
func (r *Registry) MergeUserPlugins(plugins []Flag) {
    for _, f := range plugins {
        r.flags[f.Key] = f  // user_* 前缀由创建端保证
    }
}
  • 新增 migration：user_plugin 表（id, slug, manifest_json, status, created_at, updated_at）
  • 命名空间约定：用户插件 key 必须 user_ 前缀，IsKnownKey() 对非 user_ 前缀仍只查 BuiltinCatalog
  • experimental_pref 表不需改——它只存 flag_key 字符串，user_* 自然兼容
  • 前端 loadFlagDescriptors() 已支持从服务端合并——服务端多返回用户插件即可
Phase 1 · 目录扫描式插件（1-2 周）

文件系统插件发现 + 零代码运行

用户在 ~/.multica/plugins/<slug>/ 放置插件包，服务端启动时扫描。

~/.multica/plugins/
└── my-forecast-lab/
    ├── manifest.json      # 标准 multica.dev/experiment/v1
    ├── run.sh             # 可选：子进程入口
    ├── skills/            # 可选：SKILL.md 文件
    └── ui/                # 可选：静态 HTML（iframe 渲染）
        └── index.html
  • 服务端：新增 plugin_scanner.go，ScanUserPlugins(dir) 返回 []Flag，在 main.go 的 NewRegistry() 之后调用 MergeUserPlugins()
  • 桌面端：manager-factory.ts 的 loadFlagDescriptors() 从 /api/experimental-flags 获取合并后的完整列表，resolveGenericSubprocessManager() 零改动即可 spawn 用户插件的 binary
  • IPC：通用 experimental:<flagKey>:<verb> 通道自动覆盖
  • Proxy：ProxyRoutes() 自动从 manifest 注册——用户插件的 subprocess 自动获得反向代理
  • UI：阶段一用 iframe 渲染 ui/index.html，通过 loopback proxy 同源嵌入

这个阶段结束时，一个懂 manifest 规范的用户已经可以「放文件 → 重启 → 看到插件 → 启用 → 使用」。

Phase 2 · 低代码创建 + 标准 UI Shell（2-3 周）

对话式插件创建 + 通用面板

2a. 创建流水线

将 agent_creation_studio 升级为完整的插件工坊（Plugin Workshop）：

  • 表单模式：选择插件类型（自驱/任务绑定）→ 填写名称/描述 → 选择资源（创建智能体/技能/自动化）→ 选择运行模式（无/子进程/inline）→ 生成 manifest → 安装
  • 对话模式：用户描述需求（「我需要一个每天分析 GitHub PR 质量的自动化插件」）→ 智能体生成 manifest + 资源 → 用户确认 → 安装
  • API：POST /api/user-plugins 接受完整 manifest JSON + 资源清单，服务端验证 → 写入 user_plugin 表 → 合并到 Registry → 通知桌面端刷新 flag 列表

2b. 通用 Lab Shell 组件

替代一对一手写视图，用 manifest 的 spec.ui 块驱动：

标准 Shell 组件复用现有基础设施：

  • artifacts tab → 复用 interactive-chart artifact kind（Recharts line/bar/scatter/heatmap）
  • table tab → 新增通用表格组件（数据源为插件 HTTP API）

Phase 3 · 插件生命周期管理（1-2 周）

CRUD + 版本 + 热重载

  • CRUD API：GET/POST/PUT/DELETE /api/user-plugins，每个操作触发 Registry 增量更新
  • 热重载：WebSocket 推送 user_plugin_changed 事件 → 前端 invalidate experimental-flags query → sidebar/LabPicker 自动刷新
  • 版本管理：user_plugin 表加 version 列，更新时保留旧版本行（forward-only 原则），回滚 = 切换 active version
  • 卸载：调用 RunRollback() → visibility 行 hide → lock 行释放 → 子进程停止 → 从 Registry 移除
  • 导入/导出：插件包 = tar.gz(manifest.json + resources/)，CLI multica plugin import|export
Phase 4 · 高级能力（可选，2-3 周）

沙盒强化 + 插件间协同

  • 进程沙盒：macOS sandbox-exec profile 限制子进程的文件/网络访问范围
  • 插件间通信：通过 Multica 后端中转（不直接通信），例如插件 A 的智能体可以调用插件 B 提供的技能
  • 实验快照：插件运行状态可保存/恢复，用于 A/B 对比实验
  • 插件模板库：预置常见模式（定时分析、对话助手、数据管道），用户从模板 fork 后定制

6. 安全与隔离模型

单用户本地部署大幅降低了安全复杂度，但仍需防御自伤（用户插件 bug 导致主进程崩溃/数据损坏）：

威胁防御层现有基础
子进程崩溃 manifest safety.panic_recover: true + 断路器 已有 safety.go panic/5xx_burst/init_timeout → blacklist
资源耗尽 manifest safety.burst 限流 + 子进程 cgroup/ulimit 部分 burst 已有，cgroup 需新增
网络外泄 manifest safety.ip_allowlist: ["127.0.0.0/8"] 已有 但当前是声明式，未强制执行
数据库破坏 用户插件不直接访问 PG——只通过 Multica REST API 架构保证 子进程无 DATABASE_URL 环境变量
文件系统越权 Phase 4: macOS sandbox-exec 限制读写路径 待建
主进程注入 inline 类插件不执行用户代码——只注册资源行（agent/skill/autopilot） 架构保证 inline 插件无代码执行面
关键安全原则
  • inline 插件 ≠ 代码执行：inline 类用户插件只创建数据库行（agent/skill/autopilot），不运行任意代码。代码执行只发生在 subprocess 类插件的独立进程中。
  • 子进程无特权：不注入 DATABASE_URL、JWT_SECRET。需要 Multica API 时，注入 scoped token（只读 + 限定 workspace）。
  • forward-only：用户插件的 migration 只允许 ADD COLUMN / CREATE TABLE，不允许 DROP。通过 manifest 声明的 migration SQL 在服务端审核执行。

7. 风险矩阵

风险概率影响缓解
前端动态 UI 复杂度失控 高 高 阶段一用 iframe 兜底；标准 Shell 只支持 4 种 tab kind；不引入 Module Federation
Catalog 双层结构引入 flag 评估 bug 中 高 用户 flag 必须 user_ 前缀；DefaultFor() 对未知 key 返回 false 的兜底不变
子进程资源泄漏 中 中 init_watchdog.go 已有超时 kill；追加 PID 追踪 + 父进程退出时 SIGKILL 子进程树
用户插件与内置 flag 命名冲突 低 中 user_ 前缀强制；IsKnownKey() 先查 builtin 再查 user
i18n 覆盖不全 中 低 manifest 的 LocalizedString 只需 en+zh；用户插件自带 title/description，不走 i18next
违反 fork 本地化契约 低 中 用户插件系统不涉及遥测/自动更新/OAuth/云功能——与退役清单无交集

8. 建议路线图

阶段内容工期交付物前置依赖
P0 双层 Catalog + user_plugin 表 + 命名空间 1 周 migration + plugin_scanner.go + IsKnownKey() 改造 无
P1 目录扫描 + subprocess 零代码运行 + iframe UI 1-2 周 用户放文件 → 重启 → 插件可用 P0
P2a Plugin Workshop（升级 agent_creation_studio） 1-2 周 表单/对话式创建完整插件包 P0
P2b 标准 Lab Shell 组件（4 种 tab kind） 1-2 周 manifest 驱动的通用面板替代手写视图 P1
P3 CRUD API + 热重载 + 导入/导出 1-2 周 完整插件生命周期管理 P2a + P2b
P4 沙盒强化 + 插件间协同 + 模板库 2-3 周 生产级安全 + 高级能力 P3

推荐策略：P0 → P1 → P2b 先行，P2a 与 P2b 可并行。

P0+P1 用 2-3 周交付一个「放文件就能跑」的最小插件系统，验证 manifest 驱动的全链路。P2b（标准 Shell）优先于 P2a（创建流水线），因为 Shell 同时惠及现有 6 个内置 lab——将 claude-lab-view.tsx（1300+ 行）等手写视图逐步迁移到 manifest 驱动，减少维护负担。

P4 的安全强化可以在 P1 之后任何时候插入，取决于用户插件是否开始执行不可信代码。只要用户插件限于 inline 类型（只创建数据库行），P4 可以推迟。

不建议做的事

  • 不引入 Module Federation / SystemJS——在 Electron 沙盒内动态加载远程 React 组件的安全和稳定性代价远超收益。iframe 足以覆盖 90% 场景。
  • 不做插件市场 / 远程 registry——单用户 fork，本地 tar.gz 导入/导出足够。
  • 不让用户插件直接访问 PG——所有数据交互通过 Multica REST API，保持 P0 数据安全的 guard 不被绕过。
  • 不在阶段一做热重载——重启即刷新，避免引入运行时 Registry 变异的并发问题。
