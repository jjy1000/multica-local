# Multica 0.3.1 — 4-P1 Stability Patch

## Why this exists

The 0.3.0 standalone release (Postgres.app native PG, no Docker) shipped with
4 high-severity stability/reliability P1s not addressed in the audit-fix PR.
None are P0 data-loss (the destructive-migration double-guard holds), but
all are real bug scenarios that can be triggered on the current 0.3.0 build.

This plan fixes only the high-severity P1s (4 items). The remaining 5 P1s
(hdiutil detach leak, MIGRATION_TABLES set, pg_restore --jobs=4 partial,
daemon start race, pgrep -f multi-install) are scheduled for 0.3.2 in
`.omc/plans/0.3.2-quality-pass.md` (TODO).

## Acceptance criteria

1. **P1.1**: Two concurrent `ensureServerUp` calls return the SAME `Promise`
   (no double-spawn). Test pins behavior.
2. **P1.2**: `stopServerManager` waits for in-flight `ensureServerUp` to
   complete (resolve or reject) before sending SIGTERM. Test pins.
3. **P1.6**: `probeMulticaPg` returns `false` against a PG that has
   `multica` user + db + pgcrypto but is missing `schema_migrations`. Test
   pins.
4. **P1.8**: `runMigrationFlow` writes a `O_EXCL` in-progress sentinel
   BEFORE `pg_restore`, then atomically renames it to the final sentinel
   AFTER row-count verify. A SIGKILL between pg_restore-success and
   rename-sentinel leaves the in-progress sentinel → next launch resumes
   correctly (skip with "incomplete" state, no re-migration).
5. `pnpm typecheck` 0 errors
6. `pnpm test` 268 + 7 = **275 tests green**
7. `cd server && go test ./...` all green
8. `pre-update-snapshot.sh` exits 0

## Implementation steps

### Step 1 — P1.1: in-flight guard on `ensureServerUp`

**File**: `apps/desktop/src/main/server-manager.ts:500`

Pattern (mirror `daemon-manager.ts:868-878` `withGuard`):

```ts
let inflightEnsure: Promise<ServerStatus> | null = null;

export async function ensureServerUp(profile: string, apiUrl: string): Promise<ServerStatus> {
  if (inflightEnsure) return inflightEnsure;
  if (currentState.state === "running") return currentState;
  inflightEnsure = (async () => {
    try {
      return await runEnsureServerUp(profile, apiUrl);
    } finally {
      inflightEnsure = null;
    }
  })();
  return inflightEnsure;
}
```

Rename existing body to private `runEnsureServerUp`. The IPC `server:ensure-up`
handler still calls `ensureServerUp`. Concurrent IPC fires from the renderer
2s poll now coalesce.

**Test**: `server-manager.test.ts` — call `ensureServerUp` twice via
`vi.useFakeTimers()` + deferred resolve on a mocked `startServer`. Both
calls must resolve to the same value with only ONE `startServer` invocation.

### Step 2 — P1.2: stop vs in-flight race

**File**: `apps/desktop/src/main/server-manager.ts:477-491` (stopServer) + `:583` (ensureServerUp success path)

Add module-level `stopping: boolean` flag. `stopServerManager` sets it to
true before any await. `runEnsureServerUp` checks after every await:
"if (stopping) return currentState" — exits cleanly without writing
`currentState = "running"` for a now-killed server.

Also fix `stopServer` to `await inflightEnsure` (if any) before killing
the child process. Order:

1. `stopping = true`
2. `await inflightEnsure` (waits for any in-flight to settle)
3. `await stopNativePg()` (existing)
4. `stopServer()` (existing SIGTERM/5s/SIGKILL)

**Test**: inject a deferred `startServer`, call `ensureServerUp`, then
call `stopServerManager`. Verify `currentState.state === "stopped"` at
the end and no orphan child. (Hard to test fully without real child
process; smoke-test with deferred promise only.)

### Step 3 — P1.6: probeMulticaPg false-positive

**File**: `apps/desktop/src/main/server-manager.ts:752-798`

Add a fourth psql probe: after user/db/pgcrypto check, query
`information_schema.tables` for `schema_migrations`. If absent, return
`false`. This is the table the multica migrate binary creates on first
initdb — a foreign PG (even with matching user/db/pgcrypto) will not
have it.

Concrete SQL change at `:778`:

```sql
SELECT current_user || '|' || current_database() || '|' ||
  CASE WHEN EXISTS(SELECT 1 FROM pg_extension WHERE extname='pgcrypto') THEN 't' ELSE 'f' END ||
  '|' || CASE WHEN EXISTS(SELECT 1 FROM information_schema.tables
                            WHERE table_name='schema_migrations' AND table_schema='public')
              THEN 't' ELSE 'f' END
```

Update `:789` to require `user === "multica" && db === "multica" && pgcrypto === "t" && schemaMigrations === "t"`.

**Test**: stub `probeMulticaPg` via existing test surface — but this
function spawns real psql. Add a NEW vitest file `probe-multica-pg.test.ts`
that uses `vi.mock("node:child_process")` to inject a fake `spawnSync`
returning pre-canned stdout for the 4-field probe. Assert:
- All 4 fields correct → true
- Missing `schema_migrations` field → false
- Wrong user → false

### Step 4 — P1.8: sentinel atomicity

**File**: `apps/desktop/src/main/pg-bootstrap.ts:881` + `:923-1066`

Current order: probe Docker → pg_dump → pg_restore → verify → write sentinel.
Bug: SIGKILL between restore-success and sentinel-write means next launch
re-runs full migration; catch block wipes pgdata → data loss.

New order with `O_EXCL` in-progress marker:

```ts
const SENTINEL_IN_PROGRESS = join(homedir(), ".multica", ".pg-migrating-v1");
const MIGRATION_SENTINEL = join(homedir(), ".multica", ".pg-migrated-v1");

// At start of runMigrationFlow (after Docker check + user-confirm):
let createdInProgress = false;
try {
  const fd = openSync(SENTINEL_IN_PROGRESS, "wx", 0o600); // O_EXCL
  writeSync(fd, `started-at=${new Date().toISOString()}\n`);
  closeSync(fd);
  createdInProgress = true;
} catch (err) {
  if ((err as NodeJS.ErrnoException).code === "EEXIST") {
    // Another migration is in progress OR was interrupted. Refuse to
    // start a fresh one. Surface "incomplete previous migration" and
    // let user manually clear (or auto-clear on next launch if
    // pgdata was wiped — we handle this in startNativePg).
    return { skipped: true, reason: "already-migrated" };
  }
  throw err;
}

try {
  // ... existing pg_dump + pg_restore + verify ...
  // On success:
  renameSync(SENTINEL_IN_PROGRESS, MIGRATION_SENTINEL);
  return { ok: true, ... };
} catch (err) {
  if (createdInProgress) unlinkSync(SENTINEL_IN_PROGRESS); // best-effort
  // existing wipe-pgdata + rethrow
  throw ...;
}
```

Additionally: on the next launch, `startNativePg` checks
`SENTINEL_IN_PROGRESS` existence. If present AND `pgdata/PG_VERSION`
exists (meaning initdb already ran) BUT `MIGRATION_SENTINEL` doesn't —
that's an interrupted migration. Wipe pgdata, unlink the in-progress
sentinel, let the user re-confirm.

**Tests** (`pg-bootstrap.test.ts`):
1. `runMigrationFlow` skips with `already-migrated` when in-progress sentinel exists
2. After successful migration, the sentinel file is renamed (verify by stubbing)
3. After failure, the in-progress sentinel is unlinked (verify by stubbing)

These tests need a more involved mock setup — `execFileSync` for `docker`
+ `pg_dump` + `pg_restore` + the sentinel fs ops. We can use `vi.mock`
on `node:fs` selectively.

## Risks and mitigations

| Risk | Mitigation |
|------|-----------|
| P1.1 cache returns stale Promise across quit/restart | Clear `inflightEnsure = null` in `stopServerManager` |
| P1.2 `stopping` flag never resets on quit → next launch stuck | `stopServerManager` reset `stopping = false` in `finally` |
| P1.6 adding 4-field probe slows it down (~3ms extra SQL) | Acceptable; probe runs once per launch |
| P1.8 O_EXCL race between two concurrent runMigrationFlow calls | The IPC handler `server:run-migration` is single-fire (user clicks button), so low risk; add EEXIST guard returns "skipped/already-migrated" anyway |
