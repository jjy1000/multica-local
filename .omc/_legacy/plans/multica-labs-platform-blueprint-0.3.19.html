Multica Labs 平台蓝图

把 Labs 升级为与 Multica 强集成的实验环境

当前 Labs 是五个 flag 的集合：每个 flag 都要触碰 catalog、handler、manifest、IPC、sidebar、CLI、技能、安装器、运行时与安全网。本蓝图把分散的"私有舞台"收敛到一份开发者可声明、平台自动装配的统一实验契约。所有实验功能都通过 workspace、agent runtime、Skill、权限、资源、UI 渲染、生命周期与安全网进入 Multica；不允许独立长成应用、也不允许拥有"私有入口"。

2. 意图与边界

用户原话（2026-07-14） "把实验室作为开发者环境+基础。我可以在其中部署和开发其他实验功能……这些功能都不允许独立开发，必须适配 Multica 的环境。"

2.1 实验室的定位

  • 实验室是基础设施，不是应用集合。开发者声明实验，平台装配实验。
  • 实验寄生在 Multica 内：workspace、agent runtime、Skill、权限模型、UI 框架、安全网都是宿主；实验不能自己带一套。
  • 实验在实验室中可自由渲染、自由运行，但渲染走 packages/views/<name>-view，运行走 multica experimental run <name>；两者都不能脱离 Multica 入口被发现。
  • 成熟后才考虑集成到主产品：蓝图终点是"毕业通道"，主产品路径不复用实验代码，只接受 catlog DefaultVal=true 的迁移。

2.2 非目标（明确不做）

  • 不做动态插件加载、不做用户上传 manifest、不做"插件商店"。
  • 不做新 IPC 总线；实验在 /__experimental/upstream + /experimental/<name>/* + useExperimentalFlag("<name>", false) 三条已有管道内复用。
  • 不引入新的 feature-flag 框架；继续在 server/pkg/featureflag 框架 + experimental.Catalog 单一权威源内扩展。
  • 不放开 namespace；所有实验命名挂在 experimental. 之下，禁止污染主产品路径。

3. 统一实验契约（核心）

每个实验是一个 Manifest 描述的命名单元，由 experiments/<name>/manifest.yaml（dev 路径）与 apps/desktop/resources/experiments/<name>/manifest.json（打包路径）共同提供。下面是必须字段，可选字段在 附录 A。

# experiments/<name>/manifest.yaml（dev）→ manifest.json（packaged）
apiVersion: multica.dev/experiment/v1
kind: Experiment
metadata:
  name: code_canvas             # 唯一，kebab-case，禁止与主产品 namespace 重名
  flag: code_canvas             # 与 server/internal/experimental/catalog.go 里的 Key 一致
  title: { en: "Code Canvas", zh: "代码画布" }
  description: { en: "...", zh: "..." }
  # 默认 off。新增实验一律 false。开启后才需要以下字段被实际读取。
  default_enabled: false
  # 开发者拥有；用户不能建/改 flag。
spec:
  # —— 工作区：所有实验都寄生在专有 workspace（reserved slug）里
  workspace:
    reserved_slug: code-canvas        # 必须加入 reserved_slugs.json
    name: "Code Canvas 实验室"
    description: "..."
  # —— 能力：实验需要 Multica 提供什么
  capabilities:
    skills: [code-canvas-tools]       # 挂载的 Skill key（见下 5.5）
    agents: [code_canvas_mentor]      # 实验专属 agent（runner 内创建）
    squads: [code-canvas-squad]       # 实验专属 squad
    mcp_servers: []                   # 0 起步，未来按需扩展
    permissions:                      # 复用 platform-level 权限枚举
      - "issue:read"
      - "issue:write"
      - "agent:invoke"
  # —— 入口：实验在宿主内的可见位置（只有这些位置允许出现实验 UI）
  entry_points:
    sidebar:
      - { key: code_canvas, label_key: sidebar.code_canvas, route: /experimental/code-canvas }
    settings:                         # 可选：直接进 Labs 卡片里的"打开"按钮
      route: /experimental/code-canvas
    command_palette: []               # 0 起步
  # —— 运行时：实验如果需要本地进程，声明它
  runtime:
    kind: subprocess                  # enum: subprocess | inline | headless
    binary: code-canvas/run.sh        # 相对 resources/ 子目录
    args: []                          # 启动参数；平台追加 free port
    health_path: /health
    env:                              # 注入到子进程；平台自动追加 MULTICA_API_URL+MULTICA_API_TOKEN
      CODE_CANVAS_MODE: multica
    ready_timeout_ms: 30000
    stop_grace_ms: 5000
    on_ready:   registerUpstream      # platform 调用 experimental_proxy.SetLoopbackURL
    on_stop:    unregisterUpstream
    on_missing: "service not bundled — drop the binary into apps/desktop/vendor/code-canvas/ and re-run bundle-cli"
  # —— 资源：实验的领域数据如何生成/隐藏/锁
  resources:
    installable: true
    lockable_resources: [workspace, skill, agent, squad, member, mcp_server]
    install_handler: code_canvas_install    # 命名 handler，平台按名字 dispatch
    rollback_handler: code_canvas_rollback
    visibility_table: experimental_resource_lock   # 复用 0.3.15 lock 表
  # —— 安全：实验自带安全上下文
  safety:
    init_timeout_ms: 30000             # 平台 RunWithTimeout 包裹 init
    burst: { threshold: 3, window: 60s }   # 平台 ExperimentalFlagBurst 包裹子路由
    panic_recover: true                # 平台顶层 defer 捕获并 MarkBroken
    ip_allowlist: [127.0.0.0/8]        # 实验注册 loopback 端点时强制
  # —— 观察：实验的所有可观察信号走同一组端点
  observability:
    logs: ~/.multica/logs/experiments/<name>.log
    metrics: registered_under("labs.")
    health_ipc: experimental..status
  # —— 出口：实验向哪几个 host 协议暴露
  surface:
    proxy_prefix: /experimental/code-canvas
    loopback_service: code_canvas
  # —— 毕业通道
  graduation:
    # 把这个实验从 Labs 移到主产品的入口：
    # 1. catalog.DefaultVal = true
    # 2. 删除本 manifest（features/<name>.go 接管）
    # 3. schema_migrations 注册 row
    promote_to: features/code_canvas
    auto_disable_after: 0    # 毕业不主动关停，由开发者删 manifest
契约的硬约束（用户决定于 2026-07-12，仍适用于 0.3.19）
  1. flag=off 完全 bypass：实现里的每一行新代码必须被 if useExperimentalFlag(...) || catalog.DefaultFor(...) 包裹；旧路径不能 import 实验代码。
  2. 用户不能建 flag：Labs UI 只渲染 catalog 数组，contract 不暴露 create/edit。
  3. 仅 Labs tab 入口：sidebar 入口的可见性完全由 entry_points.sidebar[*].flag 驱动，禁止在 nav 顶栏、command palette 之外出现实验。
  4. 不是插件系统：不暴露动态加载、不暴露用户上传 manifest；manifest 是开发者 commit 进仓库的资源。

5. 分阶段实施（10 个 PR）

每个 PR 都是 single-feature、self-contained、可独立 ship。PR 之间的依赖在 依赖图 一节集中说明。

P1 · Catalog 扩展（Opus，1 PR）

扩展 Flag 结构体加入 manifest 引用 + capability 列表，让 Catalog 成为契约的 server-side 真源。

改动

  • server/internal/experimental/catalog.go：Flag 增加 ManifestPath string、Capabilities []Capability、RuntimeKind string、ProxyPrefix string、LoopbackService string 字段；保持 Key/DefaultVal/Title/Description 不变。
  • 新增 server/internal/experimental/manifest.go：LoadManifest(flagKey string) (*Manifest, error)，在 MULTICA_RESOURCES_DIR/experiments/<flagKey>/manifest.json 与 dev 的 apps/desktop/resources/experiments/<flagKey>/manifest.json 之间回退。
  • 5 个 catalog 条目逐一在源里加 ManifestPath + RuntimeKind + ProxyPrefix。Claude Science = inline（无子进程），Pythia = subprocess，Mythos = headless，其它 = none。
  • 新增 manifest_test.go 5 个 case：catalog 每条 flag 必须有 manifest；manifest 必须经过 json schema 校验；ReservedSlugs 中的 claude-science/pythia-oracle/mythos-swarm 必须在 manifest 出现且 manifest slug 一致。

退出标准

  • go test ./internal/experimental/... PASS；typecheck 0 错。
  • 5 个 flag 全部带 manifest，LoadManifest 在 dev / packaged 都能 resolve。
  • API 行为不变（GET /api/experimental-flags 仍 200，shape 仍 {flags: [...]}，见 验证）。

回滚

只动 Flag 结构体的 JSON 字段（omitempty），对外 wire 形态不变；回滚 = git revert + 重跑 go test。

P5 · Skill 适配器（Opus，1 PR，风险高，详见 R11）

实验拥有专属 Skill 时，由平台在 运行时 注入 SKILL.md。当前 server/internal/service/builtin_skills.go:10-11 用 go:embed builtin_skills 把整目录在编译期固化，无法按 flag 动态增减；本 PR 必须把"编译期 embed"改为"boot 期扫描 MULTICA_RESOURCES_DIR/skills/<flagKey>/ + 仅对 useExperimentalFlag(key) 命中的 flag 暴露"。

改动

  • server/internal/service/builtin_skills.go：保留 go:embed 作为"主产品 skill"来源，追加 boot 阶段 loadExperimentalSkills(queries, flagSnapshot)：扫描 MULTICA_RESOURCES_DIR/skills/<flagKey>/<name>/SKILL.md，仅当 flagSnapshot.IsEnabled(flagKey) 为 true 时挂入 Skills slice。主产品 embed 不动（保证 0.3.6 前的 skill 行为零变化）。
  • 每个实验的 SKILL.md 模板：固定 frontmatter multica.experiment: <flagKey>，让 loader 识别其归属。Skill body 仍由开发者写。
  • 安全：loopback 端点（/api/runtime/llm-call）和 __experimental/upstream 仍只接受 127.0.0.0/8 + JWT + 60/min（runtime_llm_call.go:64-100），manifest safety.ip_allowlist 字段以"附加白名单"语义合并（不替换默认）。
  • 测试：builtin_skills_test.go 验证 flag=off 时不读盘、flag=on 时加入列表、SKILL.md frontmatter 缺失或 experiment 字段不匹配则 fail fast。Boot 路径并发安全：读盘必须 mutex + 只在 boot 跑一次。

退出标准

  • 已有 multica-claude-science / multica-pythia / multica-mythos 三个 SKILL.md 加上 frontmatter；新增实验挂 SKILL.md 不再改 server handler / mount 点。
  • loader 在 flag=on 后 200ms 内把新 skill 加入 list；agent 匹配命中。
  • 主产品 9 个 embed skill 行为零变化（multica-mentioning / multica-working-on-issues / 等）。

P6 · 资源生命周期（Opus + Sonnet，1 PR）

9. 非目标与延后

  • 动态插件商店 / 用户上传 manifest：违反硬约束 2，永久不做。
  • Web build 的 Labs：0.3.18 起 web 已支持，api.listExperimentalFlags() 可用；但 runtime 沙箱只 desktop。Web 用户看到的是 flag 状态 + Skills 列表，runtime 端点 502 + 友好提示。
  • Mobile Labs：apps/mobile 当前不挂任何实验，1.0 不变。
  • 实验间共享 runtime：未来版本再考虑，本期 1 个实验 = 1 个独立进程（与 0.3.18 现状一致）。
  • 实验自我升级：实验不能在用户运行时改自己的 manifest；只允许开发者在 PR 升级。
  • 热重载 manifest：必须重启 Multica 才生效；防止实验改 schema_migrations 拖垮进程。
