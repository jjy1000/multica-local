# 0.5.102 — board-dedupe hotfix (2026-09-07)

## Symptom

Desktop 0.5.101 board rendered N duplicate cards for a single created issue
(e.g., 5× JYF-439 in 待办 column after creating "拟写相关方案", 4× JYF-221 in
进行中 column for an earlier-created issue). Server-side was clean (1 POST
`/api/issues` → 201, 1 `INF issue created` log entry per click — verified via
`server.log` 09:38:28 create event and 4 earlier samples). The duplication was
entirely client-side cache → render.

## Root cause (3 dedupe gaps in the issue-list pipeline)

The cache shape is `{byStatus: {todo: {issues, total}, in_progress: {...}, ...}}`
with 7 paginated categories. Each stage of the pipeline had a dedupe gap:

1. **`addIssueToBuckets`** (`packages/core/issues/cache-helpers.ts:41`) — only
   checked the resolved category bucket. If the same id had already landed in
   another bucket from a prior bug or a different `category` resolution across
   invocations, the new push still appended a row to the target bucket.
2. **`flattenIssueBuckets`** (`packages/core/issues/queries.ts:149`) —
   `out.push(...bucket.issues)` over 7 buckets with no id dedupe. A bucket
   containing duplicates stayed duplicated in the flat array.
3. **`buildColumns`** (`packages/views/issues/utils/drag-utils.ts:45`) —
   pushed every issue id into its column without `seen` tracking. The board's
   `issueMap` (Map.set) dedupes by id, but `issueIds` (the array fed to
   `<SortableContext>` and `resolvedIssues.flatMap`) was allowed to carry
   duplicates straight to render.

## Fix (commit `d6f918c6c`, 6 files / +107 / −5)

- `addIssueToBuckets` now scans **every** bucket for the id before adding
  (cross-bucket dedupe). If the id is anywhere in `resp.byStatus`, skip.
- `flattenIssueBuckets` now maintains a `seen: Set<string>` and emits each id
  exactly once across the 7 buckets.
- `buildColumns` now maintains a `seen: Set<string>` and emits each id exactly
  once across all columns (last-line guarantee before render).

Together: every issue id lands in at most one column regardless of how the
cache got into its duplicate state. No need to pin down the upstream source of
the duplicate entries (likely multi-mount `useRealtimeSync` fan-out or stale
pre-fix cache state) — the symptoms are gone.

## Upstream note

Upstream `multica-ai/multica` (`packages/core/issues/mutations.ts:79`) has
already refactored the inline `useCreateIssue` cache logic into a shared
`useIssueCreateMutation<TVariables>` factory used by `useCreateIssue`,
`useCreateCommentSubIssue`, etc. — but the body of that factory is BYTE-IDENTICAL
to fork's inline `useCreateIssue.onSuccess` + `onSettled`. No upstream fix
addresses this dedupe gap either. Future port candidate: pull the factory
pattern (DRY) but keep the dedupe hardening fork-local.
