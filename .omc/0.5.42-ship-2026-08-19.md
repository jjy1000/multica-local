## Lessons

1. **`setQueryData` does not postpone garbage collection — critical for `staleTime: Infinity` caches.** Closing a transcript view while its run keeps streaming can have the entry disappear mid-window, and writing then REBUILDS it holding only that batch. Under app-wide `staleTime: Infinity` the next open reads the stub as fresh and never refetches. Solution: re-check the held gate immediately before each write, drop the batch if the entry is gone. Cost of drop: zero (rows are persisted, next open fetches the whole timeline). Cost of NOT dropping: silent, permanent, not self-healing.
2. **Capability routing is the principled fix for clip-on-broadcast, but the hub doesn't retain `client_version`.** So upstream wraps the clip in `MULTICA_CLIP_TASK_MESSAGE_BROADCAST` (off by default) until per-task scope routing ships. The same protocol work is waiting on for both. Documented in commit body — when scope routing lands, the env gate can be retired.
3. **Mobile's `chat_session_id` gating pre-empts `task:message` delivery** so the truncated-refetch branch on mobile is currently unreachable. Keeping the branch in place means whichever side of the delivery gap is fixed first already has the clipping-aware invalidation ready. Same defense-in-depth pattern as "wire the server side first, flip the env after".
4. **The `structuralSharing` pattern is what makes fetch + backfill + realtime-batch safe to coexist.** Three write paths all use the same query cache; without a unifying merge rule, they could disagree (a fetch response can replace the array wholesale, dropping any frame written while it was in flight). The `unionTaskMessagesBySeq` helper is the load-bearing piece — identity preservation (`changed = false → return base`) keeps duplicate events from re-rendering every subscriber.
